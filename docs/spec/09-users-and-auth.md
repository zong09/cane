# 09 · ผู้ใช้และการยืนยันตัวตน

ถอดจาก design handoff (หน้า Login และหน้า ผู้ใช้ 4 แท็บ) แล้วปิดช่องที่ design เว้นไว้
ให้ครบพอที่โมดูล `auth/` เขียนได้โดยไม่ต้องกลับไปตีความภาพ · ข้อที่มติเดิมตัดสินไว้แล้ว
หน้านี้**อ้าง ไม่ตัดสินใหม่** — [decisions.md](../decisions.md) ข้อ 16 (ไม่มี human gate
ต่อไม้), ข้อ 25 (การเก็บความลับของ auth), ข้อ 23 (append-only ด้วยสิทธิ์ของ DB)
และข้อ 18 (แก้ config = สร้างเวอร์ชันใหม่ ไม่ทับของเก่า)

design handoff อยู่นอก repo (`.gitignore`) หน้านี้จึง **ถอดตารางมาไว้ในตัวเอง** ไม่ลิงก์ไปที่นั่น

## 1. ขอบเขต

หน้านี้ตัดสินสามอย่าง: **ใครเป็นใคร** (บัญชี role สถานะ) · **พิสูจน์ตัวตนอย่างไร**
(password + TOTP, session, การล็อก) · **ใครทำอะไรได้** (ตารางสิทธิ์กับ endpoint ที่ผูกไว้)

ที่หน้านี้ **ไม่** ตัดสิน: หน้าตาของหน้าจอ (design handoff), ลำดับงานต่อการปิดแท่ง
([08](08-runtime-pipeline.md)), การแจ้งเตือน ([11](11-notifications.md))

**คำที่ต้องไม่สับสน**

| คำ | ความหมาย |
| --- | --- |
| **สิทธิ์** (capability) | ทำ action นั้นได้หรือไม่ — ผูกกับ role ตามตารางข้อ 3 |
| **step-up** | ขอ TOTP ซ้ำก่อนลงมือ — **ไม่ใช่สิทธิ์** เป็นการยืนยันว่าคนที่นั่งอยู่ยังเป็นเจ้าของบัญชี |
| **โหมด** (live/paper) | มุมมองว่ากำลังดูโปรไฟล์ไหน **ไม่ใช่ control** — ดู [10](10-engine-and-console.md) |

## 2. บัญชี role และสถานะ

**5 role** `OWNER` `ADMIN` `TRADER` `VIEWER` `AUDITOR` — สิทธิ์ผูกกับ role ไม่ผูกกับคน
ย้ายคนข้าม role ได้ แต่ไม่มีการให้สิทธิ์พิเศษเฉพาะคน

**3 สถานะ** ของบัญชี

| สถานะ | เข้าคอนโซลได้ | เกิดเมื่อ |
| --- | --- | --- |
| `pending` | **ไม่ได้** | ถูกเชิญแล้ว แต่ยังไม่ตั้งรหัสผ่านหรือยังไม่ผูก TOTP ครบ |
| `active` | ได้ | ตั้งรหัสผ่านและผูก TOTP เสร็จแล้ว |
| `suspended` | **ไม่ได้** | OWNER/ADMIN ระงับ — session ที่เปิดอยู่ถูกตัดทันที |

**บัญชีที่ยังไม่ผูก TOTP เข้าคอนโซลไม่ได้เลย ไม่ใช่แค่เตือน** — เงื่อนไขนี้อยู่ที่ขั้นตอน
login ไม่ใช่ที่หน้าจอ ถ้า `totp_enrolled_ts IS NULL` การ login จบที่ขั้นที่ 2 ไม่ผ่าน
ไม่ว่ารหัสผ่านจะถูกก็ตาม

**สองข้อบังคับที่ต้องอยู่ในโค้ด ไม่ใช่ในวินัยของคนกด**

- **ห้ามเหลือศูนย์ OWNER** — ระงับหรือย้าย role ของ OWNER คนสุดท้ายต้องถูกปฏิเสธ
  ระบบที่ไม่มี OWNER แก้ profile และสลับ `dry_run` ไม่ได้อีกเลย และไม่มีทางกู้จากในคอนโซล
- **ระงับตัวเองไม่ได้** และ **ตัด session ของตัวเองจากหน้า session ไม่ได้** (ออกจากระบบใช้ปุ่ม logout)

**OWNER คนแรกไม่ได้มาจากคำเชิญ** — ยังไม่มีใคร login ได้ตอนตั้งเครื่อง จึงสร้างผ่าน CLI
ที่มีอยู่แล้ว (`cane` — ที่เดียวกับ `cane db seed`) คำสั่งนี้รับอีเมลกับรหัสผ่านตั้งต้น
แล้วสร้างบัญชี `pending` ที่ role `OWNER` · การผูก TOTP ยังต้องทำผ่านคอนโซลเหมือนคนอื่น
เพื่อไม่ให้มีเส้นทางไหนที่ข้าม 2FA ได้

### สิ่งที่ตารางนี้ไม่มี และทำไม

- **ไม่มีสิทธิ์ "กดยืนยันเข้าไม้"** — [decisions.md ข้อ 16](../decisions.md) ตัดออกแล้ว
  เพราะขัดกับข้อ 7 ตรงๆ design handoff ชุด v3 ยังมีอยู่ นั่นคือ **errata ของ design**
  ไม่ใช่มติที่รอทบทวน · คนกดได้สองอย่างคือ `choose_cold_start_route` กับ
  `close_position_manual` ทั้งคู่เป็นการลดความเสี่ยงหรือเลือกไม่ทำ ไม่มีปุ่มไหนที่คนกดแล้วเปิดไม้ใหม่
- **ไม่มีสิทธิ์ "สลับโหมด live/paper"** — โหมดคือมุมมอง ทุก role ที่ login ได้สลับได้
  สิ่งที่กั้นการเข้าไปดู `live` คือ **step-up** (ข้อ 6) ไม่ใช่สิทธิ์ · ถ้าทำเป็นสิทธิ์
  VIEWER กับ AUDITOR จะดู live ไม่ได้ ซึ่งขัดกับหน้าที่ของสองบทบาทนั้นทั้งบทบาท
- **`allow_short` และการตั้งค่าแจ้งเตือนไม่มีแถวของตัวเอง** อยู่ใต้ `edit_profile`
  ทั้งคู่เป็นการแก้ค่าในโปรไฟล์ การแยกแถวจะทำให้มีสามแถวที่ค่าเหมือนกันหมด
- **`killswitch_latch` กับ `killswitch_unlatch` แยกกัน** เพราะเป็นการกระทำคนละทิศ:
  latch คือหยุด (กดได้กว้าง ไม่ต้องยืนยันซ้ำ — ความช้าตอนฉุกเฉินแพงกว่าการกดเกิน)
  unlatch คือ **กลับไปยิงเงินจริง** จึง OWNER เท่านั้นและต้อง step-up
- **`engine_control` ให้ ADMIN ด้วย** เพราะ ADMIN กด `killswitch_latch` ได้อยู่แล้ว
  บทบาทที่หยุดระบบได้แต่สตาร์ทคืนไม่ได้คือกับดักตอนกลางคืน ไม่ใช่การป้องกัน

### ตารางนี้เป็น "ข้อมูล" ไม่ใช่ค่าคงที่ในโค้ด

คอนโซลแก้ตารางได้ (`manage_users` + step-up) ตารางข้างบนจึงเป็น **เวอร์ชันตั้งต้น**
ที่ `cane db seed` ใส่ลง `role_permissions` ไม่ใช่ความจริงตลอดกาล

**คอลัมน์ OWNER ล็อก** — OWNER มีสิทธิ์ทุกข้อเสมอ ข้อบังคับนี้อยู่ **ในโค้ด**
(ตัวตรวจสิทธิ์คืน `True` ให้ OWNER ก่อนแตะตาราง และ endpoint ที่บันทึกตารางปฏิเสธ diff
ที่แตะคอลัมน์ OWNER) **ไม่ใช่แค่ปิดปุ่มใน UI** — ปุ่มที่ปิดไว้เป็นความสุภาพ ไม่ใช่ข้อบังคับ

**การแก้ตารางเดินตามแบบของ [decisions.md ข้อ 18](../decisions.md)** คือสร้างเวอร์ชันใหม่
แล้วเลื่อนตัวชี้ ไม่ `UPDATE` ทับแถวเดิม เพราะบันทึก audit ที่บอกว่า "เปลี่ยน 3 ช่อง"
จะไร้ความหมายถ้าอ่านค่าเดิมกลับไม่ได้

รูปที่ต้องใช้: `permission_versions(id, created_ts, created_by, is_active)` กับ
`role_permissions(version_id, role_id, permission_id, allowed)` — `version_id` เป็นส่วนของกุญแจ
ไม่ใช่คอลัมน์ประกอบ · คอนโซลได้สิทธิ์ `UPDATE` เฉพาะคอลัมน์ `is_active` เหมือนที่ config ได้
(grant ระดับคอลัมน์) เนื้อของเวอร์ชันแก้ไม่ได้แม้แต่คอนโซล

## 4. endpoint → สิทธิ์ที่ต้องมี

ตัวตรวจสิทธิ์ต้องมี **หนึ่งแถวของตารางต่อหนึ่ง mutating endpoint** ไม่งั้นไม่มีอะไรให้เทียบ

**[10](10-engine-and-console.md) เป็นเจ้าของรายการ URL** หน้านี้ผูกสิทธิ์ให้ ไม่ได้นิยาม URL
ถ้าสองหน้าไม่ตรงกัน หน้านั้นถูก

| endpoint | `cap` | step-up |
| --- | --- | --- |
| `GET /api/{profile}/overview` · `/risk` · `GET /api/engine/status` | `view_overview` | – |
| `GET /api/{profile}/records` · `GET /api/{profile}/records/export` ดู `export_records` | `read_decisions` | – |
| `GET /api/{profile}/config` · `GET /api/config/diff` | `view_overview` | – |
| `POST /api/{profile}/engine/start` · `/stop` | `engine_control` | **ต้อง** |
| `POST /api/{profile}/killswitch/latch` | `killswitch_latch` | – |
| `POST /api/{profile}/killswitch/unlatch` | `killswitch_unlatch` | **ต้อง** |
| `POST /api/{profile}/config` (รวม `allow_short` และค่าแจ้งเตือน) | `edit_profile` | **ต้อง** |
| `POST /api/{profile}/config/dry_run` | `toggle_dry_run` | **ต้อง** |
| `POST /api/{profile}/symbols` · `DELETE …` | `edit_symbols` | **ต้อง** |
| `POST /api/{profile}/positions/{symbol}/close` | `close_position_manual` | **ต้อง** |
| `POST /api/{profile}/coldstart/{symbol}` | `choose_cold_start_route` | – |
| `POST /api/users` · `/users/{id}/role` · `/suspend` · `/unlock` · `/permissions` · `DELETE /api/sessions/{id}` | `manage_users` | **ต้อง** |
| `POST /api/users/{id}/reset-2fa` | `reset_other_2fa` | **ต้อง** |
| `GET /api/{profile}/records/export` | `export_records` | – |
| `POST /api/session/mode` | — (ทุก role) | **ต้อง เมื่อเป้าหมายเป็น `live`** |

**ค่าเริ่มต้นของ endpoint ที่ยังไม่มีในตารางนี้คือ 403** — ไม่ใช่ "ผ่านเพราะยังไม่ได้ผูกสิทธิ์"
endpoint ใหม่ที่ลืมผูกต้องพังตอนเรียกครั้งแรก ตามแบบเดียวกับ GRANT ใน
[decisions.md ข้อ 23](../decisions.md)

## 5. login สองขั้น

```
ขั้นที่ 1  อีเมล + รหัสผ่าน   →  ขั้นที่ 2  TOTP 6 หลัก  →  session
```

**ทั้งสองขั้นต้องผ่านจึงจะมี session** ขั้นที่ 1 ผ่านแล้วยังไม่มีสิทธิ์อะไรเลย สิ่งที่ได้คือ
ตั๋วชั่วคราวสำหรับขั้นที่ 2 (อายุ 5 นาที ใช้ได้ครั้งเดียว ผูกกับอีเมลนั้น) ไม่ใช่ session

**ข้อความที่คนเห็นต้องไม่บอกว่าอีเมลไหนมีบัญชี** — รหัสผ่านผิด อีเมลไม่มีในระบบ บัญชีถูกระงับ
และบัญชียังไม่ผูก TOTP ให้ผลลัพธ์หน้าจอเดียวกันหมด ส่วนที่ต่างกันไปอยู่ใน audit log
(การบอกว่า "ไม่มีบัญชีนี้" คือการยืนยันรายชื่อผู้ใช้ให้คนที่เดาอีเมล)

### TOTP

RFC 6238 · SHA-1 · 6 หลัก · ช่วง 30 วินาที · ยอมรับ **±1 ช่วง** (กันนาฬิกาเครื่องเหลื่อม)

**รหัสที่ใช้แล้วต้องใช้ซ้ำไม่ได้ในช่วงเวลาที่มันยังใช้ได้** — เก็บ counter ของช่วงล่าสุด
ที่สำเร็จไว้ต่อผู้ใช้ แล้วปฏิเสธ counter ที่ ≤ ค่านั้น ถ้าไม่ทำข้อนี้ รหัสที่หลุดตาไป
ยังยิงซ้ำได้อีก 90 วินาที ซึ่งพอสำหรับการส่งต่อด้วยมือ

TOTP secret เก็บเป็น ciphertext ตาม [decisions.md ข้อ 25](../decisions.md)
(ต้องถอดกลับได้ จึง hash ไม่ได้)

### backup code

**10 รหัส** สร้างพร้อมกันตอนผูก TOTP · **แสดงครั้งเดียวตอนสร้าง** · เก็บเป็น hash
· **ใช้ได้ครั้งละหนึ่งรหัส แล้วรหัสนั้นตายถาวร** (`used_ts`)

หน้าจอนับ **จำนวนที่เหลือ** ให้เห็น (design: `เหลือ 2 ครั้ง`) · สร้างชุดใหม่ได้เมื่อไหร่ก็ได้
และการสร้างชุดใหม่ **ฆ่าชุดเก่าทั้งชุด** ไม่ใช่เติมของที่ใช้ไปแล้ว

backup code ใช้แทน TOTP ได้ที่ **ขั้นที่ 2 ของ login เท่านั้น ไม่ใช้กับ step-up** —
step-up มีไว้ยืนยันว่าคนที่นั่งอยู่ถืออุปกรณ์ 2FA อยู่จริงในตอนนั้น รหัสที่พิมพ์เก็บไว้ในกระเป๋า
ตอบคำถามนั้นไม่ได้

### การล็อกบัญชี

**ผิด 5 ครั้งติดกัน → ล็อก 15 นาที** · **ล็อกที่ระดับบัญชี ไม่ใช่ที่อุปกรณ์หรือ IP**
เปลี่ยนเครื่องหรือล้างคุกกี้แล้วก็ยังล็อกอยู่

| ข้อ | ค่า |
| --- | --- |
| อะไรนับเป็น "ผิด" | รหัสผ่านผิดที่ขั้น 1 · TOTP หรือ backup code ผิดที่ขั้น 2 |
| อะไรล้างตัวนับ | **login สำเร็จครบสองขั้น** เท่านั้น |
| ครบ 15 นาทีแล้วเป็นอย่างไร | ลองใหม่ได้ โดยตัวนับยังไม่ถูกล้าง — ผิดอีกครั้งเดียวล็อกใหม่ |
| ปลดก่อนหมดเวลา | OWNER/ADMIN ปลดได้จากหน้าผู้ใช้ (`manage_users`) |
| นับจากไหน | `login_attempts` — เก็บทุกครั้งทั้งสำเร็จและไม่สำเร็จ พร้อม IP · `user_id` **nullable** เพราะอีเมลที่ไม่มีบัญชีก็ต้องถูกนับ (ดูย่อหน้าถัดไป) |

หน้าจอบอกเวลาที่เหลือและบอกว่าให้ OWNER/ADMIN ปลดได้ · **ไม่บอกว่าบัญชีนี้มีอยู่จริงหรือไม่**
สำหรับอีเมลที่ไม่เคยมีในระบบ ให้แสดงหน้าจอเดียวกันโดยนับ attempt ผูกกับอีเมลนั้นไว้เหมือนกัน

## 6. session

- token เป็นค่าสุ่มที่ไม่มีความหมายในตัว (opaque) **ไม่ใช่ JWT และไม่ใส่ role ลงไป**
- ใน DB เก็บ **hash ของ token** ตาม [decisions.md ข้อ 25](../decisions.md)
- cookie: `HttpOnly` · `SameSite=Strict` · `Secure` · **หมดอายุ 12 ชั่วโมง**
- **ตรวจกับตาราง `sessions` ทุก request** ไม่แคช role หรือสถานะไว้ในคุกกี้

ข้อสุดท้ายไม่ใช่รายละเอียดการทำ มันคือเหตุผลที่ข้อบังคับสามข้อนี้เป็นจริงได้:

| ข้อบังคับ | เป็นจริงเพราะ |
| --- | --- |
| ตัด session แล้ว **มีผลที่ request ถัดไป** | request ถัดไปอ่าน `revoked_ts` เจอ |
| ระงับผู้ใช้ = **ตัด session ทันที** ไม่ต้องรอ token หมดอายุ | สถานะบัญชีถูกอ่านใหม่ทุก request |
| เปลี่ยน role หรือแก้ตารางสิทธิ์ **มีผลกับ session ที่เปิดอยู่** | สิทธิ์ถูกคิดใหม่ทุก request |

ถ้าเอา role ใส่คุกกี้แล้วเชื่อ ทั้งสามข้อกลายเป็น "มีผลใน 12 ชั่วโมง" เงียบๆ

เก็บ **IP กับ user-agent** ต่อ session · design แสดงชื่อเมืองด้วย (`203.0.113.44 · Bangkok`)
ซึ่งต้องมีฐาน GeoIP — **ไม่อยู่ในเฟสนี้** หน้าจอแสดง IP ล้วน

### step-up TOTP

**ขอทุกครั้งที่ลงมือ ไม่มีช่วงผ่อนผัน** — ไม่มี "ยืนยันแล้วใน 5 นาทีที่ผ่านมาก็ผ่าน"
ทุก action ในตารางข้อ 3 ที่ทำเครื่องหมาย **ต้อง** ต้องแนบรหัส 6 หลักมากับ request นั้นเอง

ผลที่บันทึก: `user_audit_log.step_up_verified` **เป็นคอลัมน์** ไม่ใช่ความหวัง — คนอ่านย้อนหลัง
ต้องแยกได้ว่ารายการไหนผ่านการยืนยันซ้ำ

การสลับโหมดไป `live` ต้อง step-up ด้วย ทั้งที่ไม่ต้องมีสิทธิ์อะไร: **การเข้าไปอยู่ในหน้าจอ
ที่ปุ่มทุกปุ่มกระทบเงินจริงคือการเปลี่ยนบริบท** ไม่ใช่การเปลี่ยนหน้า · สลับกลับมา `paper`
ไม่ต้องยืนยัน และ **การสลับโหมดไม่แตะ engine ตัวใดเลย** ([10](10-engine-and-console.md))

## 7. คำเชิญ · reset 2FA · รหัสผ่านที่ลืม

**ระบบนี้ไม่มีตัวส่งอีเมล** — [decisions.md ข้อ 21](../decisions.md) วางการแจ้งเตือนไว้ที่
LINE/Telegram และเป็นเฟสบอท ไม่ใช่เฟสคอนโซล การใส่ SMTP เข้ามาแปลว่ามี credential ชุดใหม่
ใน `.env` และมีอีเมลที่ส่งไม่ออกให้ต้องจัดการ

**ลิงก์จึงไม่ถูกส่ง มันถูกแสดง** ในคอนโซลให้คนที่กดเห็นครั้งเดียว แล้วส่งต่อทางไหนก็ได้เอง

| ลิงก์ | อายุ | ทำอะไรได้ |
| --- | --- | --- |
| คำเชิญ | 72 ชั่วโมง | ตั้งรหัสผ่าน + ผูก TOTP **เท่านั้น** |
| ตั้ง 2FA ใหม่ (หลัง reset) | 72 ชั่วโมง | ผูก TOTP ใหม่เท่านั้น |
| ตั้งรหัสผ่านใหม่ | 72 ชั่วโมง | ตั้งรหัสผ่านเท่านั้น |

ทั้งสามชนิดเป็นกลไกเดียวกัน (token ใช้ครั้งเดียว เก็บเป็น hash ผูกกับผู้ใช้และชนิดของงาน)
ต่างกันแค่ว่าปลดล็อกให้ทำอะไร · ออกใหม่ได้จากแถวของผู้ใช้ และ **การออกใหม่ฆ่าลิงก์เดิม**

**รหัสผ่านที่ลืมไม่มีเส้นทาง self-service** — OWNER/ADMIN ออกลิงก์ตั้งรหัสผ่านใหม่ให้
(`manage_users` + step-up) เส้นทางที่คนกดเองต้องมีอีเมลจึงจะไม่กลายเป็นช่องยึดบัญชี
ซึ่งวนกลับไปที่ข้อที่ว่าระบบนี้ยังไม่มีตัวส่งอีเมล

**ระหว่างที่ยังไม่ผูก TOTP ใหม่ ผู้ใช้เข้าคอนโซลไม่ได้** — reset 2FA ทำให้บัญชีกลับเป็น
`pending` ซึ่งตรงกับข้อ 2 อยู่แล้ว ไม่ต้องมีสถานะพิเศษเพิ่ม

## 8. audit log ของผู้ใช้

**เขียนแล้วแก้ไม่ได้** ด้วยกลไกเดียวกับตารางข้อเท็จจริงอื่น — สิทธิ์ของ DB ปฏิเสธ
`UPDATE`/`DELETE` ([decisions.md ข้อ 23](../decisions.md)) ไม่ใช่ข้อตกลงระหว่างคนเขียนโค้ด

หนึ่งแถวต่อหนึ่ง action: **ใคร ทำอะไร กับใคร เมื่อไหร่ จาก IP ไหน และผ่าน step-up หรือไม่**
(`actor_user_id, action, target, detail, ip, step_up_verified, ts`)

สิ่งที่ต้องบันทึกอย่างน้อย: login สำเร็จ · login ไม่สำเร็จพร้อมเหตุ · การล็อกและการปลดล็อก
· ทุก action ที่มีสิทธิ์กำกับในข้อ 3 · การกด "แสดงค่า" credential ([11](11-notifications.md))
· การสลับโหมดไป `live`

### redaction เกิดตอนเขียน ไม่ใช่ตอนอ่าน

`detail` ผ่าน `cane.log.redact()` — **ตัวเดียวกับที่ระบบเทรดใช้** ([07](07-data-and-config.md))
— **ก่อนลง DB** เพราะตารางนี้แก้ไม่ได้ ค่าที่หลุดลงไปแล้วลบไม่ได้อีก การกรองตอนอ่าน
ทำให้ความลับนอนอยู่ในตารางถาวรโดยหวังว่าทุกเส้นทางการอ่านจะจำกรอง

`AUDITOR` อ่านตารางนี้ได้และส่งออกได้ แต่ไม่เห็นค่าคีย์ — ไม่ใช่เพราะมี filter พิเศษของ role
แต่เพราะ **ค่านั้นไม่เคยถูกเขียนลงไปตั้งแต่แรก**

## 9. ที่เก็บ

ตารางและนโยบายความลับอยู่ใน [decisions.md ข้อ 25](../decisions.md) — สรุปไว้ที่นี่เพื่อไม่ให้โมดูล `auth/`
ต้องเดา: `password_hash` เป็น **argon2id** · `sessions.token_hash` เก็บ hash ไม่ใช่ token
· `backup_codes.code_hash` เก็บ hash · `totp_secret_enc` เก็บ **ciphertext** ที่เข้ารหัส
ด้วย `CANE_SECRET_KEY` จาก `.env`

**DB dump อย่างเดียวต้องใช้เข้าระบบไม่ได้** เป็นเกณฑ์ตัดสินของทุกช่องข้างบน
และเป็นเหตุผลที่ `CANE_SECRET_KEY` กลายเป็นของที่หายไม่ได้ — หายแล้ว TOTP ของทุกคนใช้ไม่ได้

ตาราง `users` `roles` `permissions` `role_permissions` `backup_codes` `sessions`
`login_attempts` `user_audit_log` เขียนโดย role `cane_console`
ส่วน `user_audit_log` และ `login_attempts` เป็น **append-only** เหมือนตารางข้อเท็จจริง

## 10. เกณฑ์ยืนยันความถูกต้อง

ข้อบังคับที่ประกาศไว้แต่ไม่มีเทสต์ยิงให้ล้ม คือข้อบังคับที่ไม่รู้ว่ามีผลหรือเปล่า
([decisions.md ข้อ 23](../decisions.md)) — `auth/` ต้องมีเทสต์ที่ยืนยันอย่างน้อยนี้:

1. บัญชีที่ `totp_enrolled_ts IS NULL` **เข้าคอนโซลไม่ได้เลย** แม้รหัสผ่านถูก
2. ล็อกบัญชีแล้ว **เปลี่ยนเครื่อง/ล้างคุกกี้ก็ยังล็อก**
3. `VIEWER` เรียก `POST /api/{profile}/engine/start` ได้ **403**
4. ตัด session แล้ว **request ถัดไป** เด้งออก
5. เปลี่ยน role ของผู้ใช้ที่กำลัง login อยู่ **มีผลกับ request ถัดไป** ไม่ต้อง login ใหม่
6. รหัส TOTP เดิม **ใช้ซ้ำไม่ได้** ในช่วงเวลาที่มันยังไม่หมดอายุ
7. ระงับ OWNER คนสุดท้าย **ถูกปฏิเสธ**
8. diff ที่แตะคอลัมน์ OWNER ของตารางสิทธิ์ **ถูกปฏิเสธที่ endpoint** ไม่ใช่แค่ปุ่มปิดใน UI
9. `detail` ที่มีค่าคล้าย API key **ลง DB เป็น `***`** ไม่ใช่ค่าจริง
