# 06 · ความเสี่ยงและการส่งคำสั่ง

ระบบยิงออเดอร์อัตโนมัติโดยไม่มีคนกดยืนยันต่อไม้ น้ำหนักของความปลอดภัยทั้งหมดจึงอยู่ที่ชั้นนี้

## หลักการ

**Fail-closed** — ทุกกรณีที่ระบบไม่มั่นใจ ให้ไม่ทำ ไม่ใช่ทำแบบเดา ตั้ง config ไม่ครบ = โหลดไม่ผ่าน = ไม่เทรด

## สิ่งที่คนกดได้ และไม่ได้

คนกด **ไม่ได้** ยืนยันการเข้าไม้ทีละไม้ — นั่นเป็นการตัดสินใจเชิงสถาปัตยกรรมที่เลือกไว้แล้ว การใส่ human gate กลับเข้ามาจะทำให้ระบบกลายเป็นระบบกึ่งมือ ซึ่งเปิดช่องให้อคติของคนกลับเข้ามาพอดีตรงจุดที่ระบบตั้งใจตัดออก

กฎที่แท้จริงคือ **ไม่มี human gate ที่การเข้าไม้** — ไม่ใช่ว่าคนทำอะไรไม่ได้เลย

สิ่งที่คนทำได้ทั้งหมดตกอยู่ในสามกลุ่ม และทุกกลุ่ม*ลดความเสี่ยง*หรือ*เลือกไม่ทำ*:

| กลุ่ม | ตัวอย่าง |
| --- | --- |
| **หยุด / ลดความเสี่ยง** | latch kill switch · ปิดไม้ฉุกเฉิน · เปิด `dry_run` · ปิด `allow_short` |
| **เลือกเส้นทางที่สเปกเปิดทางไว้** | เลือก cold start (`wait_1h` / `trailing` / `skip`) |
| **แก้ค่าตั้งต้นแล้วโหลดใหม่** | risk limit, bucket, `leverage`, คู่เหรียญ — บันทึกเป็น config เวอร์ชันใหม่แล้ว activate ([decisions #18](../decisions.md)) |

การปลด kill switch เป็นการ*เพิ่ม*ความเสี่ยง จึงมีด่านของตัวเอง: พิมพ์ชื่อ profile ยืนยัน

**สิ่งที่ไม่มีและจะไม่มี: ปุ่มที่ทำให้เปิดไม้ใหม่นอกจังหวะสัญญาณ** ปิดไม้ฉุกเฉินคือทางออกทางเดียวของสถานะที่ค้างจาก `flip_aborted` ด้วย ([03](03-trading-rules.md))

## เพดานความเสี่ยง

| ตัว | ทำอะไร |
| --- | --- |
| `max_position_pct_long` / `max_position_pct_short` | เพดานแข็งต่อไม้ **แยกฝั่ง** ทับผลจากสูตรขนาดไม้ได้เสมอ — **ย่อขนาดลง ไม่ใช่ปฏิเสธไม้** แล้วบันทึก `capped: true` |
| `max_leverage` | เพดานอัตราทดระดับ profile — `leverage` ของ symbol ใดเกินค่านี้ = โหลด config ไม่ผ่าน |
| `min_liq_buffer_pct` | ระยะขั้นต่ำจากราคาปัจจุบันถึงราคา liquidation ที่ยอมรับได้ — ไม้ที่คำนวณแล้วเหลือระยะน้อยกว่านี้ **ไม่เปิด** ไม่ใช่ย่อขนาดลงให้พอดี |
| `max_daily_loss_pct` | ขาดทุนสะสมในวันชนเพดาน → หยุดยิงออเดอร์เปิดใหม่จนถึงวันถัดไป |
| `consecutive_loss_breaker` | แพ้ติดกัน N ไม้ (นับรวมทั้งสองฝั่ง) → latch kill switch |

ทั้งหมดไม่มีค่าตั้งต้นในโค้ด ต้องระบุใน config profile

### ตัวไหนย่อ ตัวไหนปฏิเสธ ตัวไหนตรวจตอนโหลด

สามอย่างนี้คนละกลไกกัน สับสนเมื่อไหร่จะได้ระบบที่ข้ามสัญญาณทิ้งทั้งที่ควรแค่ลงไม้เล็กลง

| ตัว | เมื่อชน |
| --- | --- |
| `max_position_pct_<side>` | **ย่อขนาด** ตอนคำนวณไม้ ([05](05-position-sizing.md)) แล้วเดินต่อ |
| `kill switch` · `max_daily_loss_pct` · `min_liq_buffer_pct` | **ปฏิเสธทั้งไม้** ตามลำดับนี้ ([08](08-runtime-pipeline.md) ขั้น 12) |
| `max_leverage` | **โหลด config ไม่ผ่าน** ตั้งแต่ก่อนระบบเริ่มทำงาน ไม่ใช่การตรวจตอนรัน |
| `consecutive_loss_breaker` | latch kill switch แล้วจากนั้นทุกไม้ใหม่ถูกปฏิเสธจนกว่าจะปลดด้วยมือ |

`max_leverage` ตรวจตอนโหลดแล้วก็จริง แต่ค่าที่ตั้งไว้ที่ **exchange** ถูกเปลี่ยนจากนอกระบบได้
ก่อนเปิดไม้จึงต้องตั้ง leverage ที่ exchange ให้ตรงกับ config เสมอ (`set_leverage`)
ไม่ใช่เชื่อว่ามันยังเป็นค่าเดิมจากครั้งก่อน

### `max_daily_loss_pct` นับอย่างไร

- **นับกำไรขาดทุนที่ยังไม่ปิดด้วย** (mark-to-market) ไม่ใช่แค่ realized — บน perp ไม้ที่ยังเปิดค้างขาดทุนอยู่คือความเสี่ยงจริงที่ยังถืออยู่ ถ้านับแต่ realized ระบบจะเปิดไม้ใหม่เพิ่มขณะที่ไม้เดิมกำลังจม
- **reset เที่ยงคืน UTC** ไม่ใช่เวลาท้องถิ่น — timeframe รายวันของ exchange อ้าง UTC อยู่แล้ว ถ้าใช้คนละเขตเวลา ขอบวันของ risk กับขอบวันของแท่งจะเหลื่อมกัน

### `min_liq_buffer_pct` คือสิ่งเดียวที่กัน liquidation

บน perp ไม้ถูกปิดโดย exchange ได้เองที่ราคา liquidation **แม้ยังไม่เกิดสัญญาณฝั่งตรงข้าม** ซึ่งขัดกับหลัก "ออกที่สัญญาณฝั่งตรงข้ามอย่างเดียว" ของเอกสารต้นทางโดยตรง

ระบบไม่มีทางกันเรื่องนี้ได้ด้วยตรรกะสัญญาณ กันได้ทางเดียวคือไม่เปิดไม้ที่ระยะถึง liquidation แคบเกินไปตั้งแต่แรก จึงต้อง fail-closed อย่างเคร่งครัด: คำนวณระยะไม่ได้ = ไม่เปิด

## Kill switch

- เป็นสถานะ **latched** — ติดแล้วติดเลย ไม่หายเองเมื่อเวลาผ่านไปหรือเมื่อ process restart
- **ปลดด้วยการพิมพ์ชื่อ profile ยืนยันเท่านั้น** (`live` / `paper`) การกด stop engine ไม่ปลด และการกด start engine ก็ไม่ปลด
- ตรวจ**ก่อนยิงทุกออเดอร์** ไม่ใช่ตรวจตอนเริ่มรอบ
- เก็บสถานะที่ `var/state/killswitch.json` **แยกไฟล์จาก engine state** — engine running กับ kill switch เป็นคนละเรื่องกันคนละ lifecycle

### kill switch latch แล้วเกิดอะไรกับ stop order ที่ค้างอยู่

**บล็อกออเดอร์เปิดใหม่ แต่ไม่ยกเลิก stop order ที่ป้องกันไม้เดิมอยู่**

fail-closed หมายถึงหยุด*ทำสิ่งใหม่* ไม่ได้หมายถึงปลดสิ่งที่ป้องกันอยู่ การยกเลิก stop ตอน latch คือการถอดเกราะออกจากไม้ที่ยังเปิดค้าง ซึ่งตรงข้ามกับเจตนาของ kill switch เอง

การ **replace** stop ให้เลื่อนตาม Slow Trail ยังทำได้ต่อขณะ latch เพราะเป็นการขยับจุดป้องกัน ไม่ใช่การเปิดความเสี่ยงใหม่

## dry_run

โหมดที่คำนวณครบทุกขั้นและเขียน `DecisionRecord` ครบ แต่ไม่ส่งคำสั่งจริง

ค่าตั้งต้นคือ `true` **แม้ใน live profile** การส่งคำสั่งจริงต้องเป็นการกระทำที่จงใจเสมอ ไม่ใช่สิ่งที่เกิดขึ้นเพราะลืมตั้งค่า

profile `paper` บังคับ `true` ตายตัว — ตั้งเป็น `false` แล้วโหลดไม่ผ่าน

## Broker interface

```
Broker
  place(order)               -> OrderResult
      order.type   = market | stop_market
      order.side   = buy | sell
      order.reduce_only : bool
      order.stop_px     : float | None       ต้องมีเมื่อ type = stop_market
  cancel(order_id)           -> None
  replace(order_id, stop_px) -> OrderResult
  open_orders(symbol)        -> [Order]
  positions()                -> [Position]
  balance()                  -> Balance
  set_leverage(symbol, x)    -> None
  set_margin_mode(symbol, mode, position_mode) -> None
```

**ทำไม interface ต้องมี order type:** cold start ทางที่ 2 บังคับให้ตั้ง stop ที่เส้น Slow Trail ทันทีที่เปิดไม้ ([03](03-trading-rules.md)) ถ้า Broker ทำได้แค่ market order ระบบก็มีทางเดียวคือประเมิน stop ฝั่ง engine ตอนแท่งรายวันปิด — ซึ่งบน perp ที่มี leverage คือการป้องกันที่ตรวจวันละครั้ง ราคากระโดดข้ามคืนเดียวก็ถึง liquidation ได้ก่อน engine ตื่น จึงเลือกวาง stop ไว้ที่ exchange จริง

**ทำไมต้องมี `replace`:** เส้น Slow Trail ขยับทุกแท่ง stop ที่วางไว้จึงต้องขยับตาม ถ้าไม่มี `replace` ต้อง cancel แล้ว place ใหม่ ซึ่งเปิดหน้าต่างเวลาที่ไม้ไม่มี stop คุ้มอยู่

**ทำไมต้องมี `open_orders`:** reconciliation ต้องเห็น stop order ที่ค้างอยู่ ไม่ใช่ดูแค่ position — ไม้ที่มี stop กับไม้ที่ stop หลุดไปแล้วมี position เหมือนกันทุกประการ

Adapter สองตัว:
- `PaperBroker` — จำลอง fill และ P&L **และต้องจำลอง stop fill ด้วย** ไม่ใช่แค่ market fill ไม่งั้นเส้นทาง cold start ทางที่ 2 จะทดสอบใน paper ไม่ได้เลย ซึ่งขัดกับหลักที่ว่า paper กับ live ต่างกันที่ค่าไม่ใช่ที่ตรรกะ
- `CcxtBroker` — ต่อ exchange จริงผ่าน ccxt สลับ venue ด้วย config

ตรรกะการตัดสินใจทั้งหมดอยู่เหนือ interface นี้ และต้องไม่รู้ว่าปลายทางเป็นอะไร

## กันสั่งซ้ำ (reconciliation)

`clientOrderId` คำนวณแบบ deterministic:

```
cane-{SYMBOL}-{bar_close_ts}-{side}-{leg}
leg ∈ { open, close, stop }
```

ถ้า process ตายกลางคันแล้วกลับมาใหม่ในแท่งเดิม มันจะพยายามส่งออเดอร์เดิม — id ที่ซ้ำทำให้ exchange ปฏิเสธหรือให้ผลเดิม แทนที่จะเปิดสถานะซ้อน

**`leg` เป็นส่วนที่ขาดไม่ได้** ด้วยสองเหตุผล: flip ยิงสองขาในแท่งเดียวและฝั่งเดียวกัน ถ้าไม่มี `leg` ขาปิดกับขาเปิดจะได้ id ชนกันเอง · และ stop order เกิดในแท่งเดียวกับขาเปิด ถ้าไม่มี `leg = stop` การกันสั่งซ้ำจะไม่นิยามสำหรับ stop เลย

นอกจากนี้ **ต้องอ่านสถานะจริงจาก exchange ก่อนตัดสินใจทุกครั้ง** ทั้ง `positions()` และ `open_orders()` ห้ามเชื่อสถานะที่จำไว้ในหน่วยความจำ — สถานะจริงเปลี่ยนได้จากนอกระบบ (คนไปกดเอง, order ถูก fill ทีหลัง, stop ทำงานไปแล้ว, exchange มีปัญหา)

## ความปลอดภัยของ credential

- API key อยู่ใน environment / ไฟล์ `.env` ที่คนกรอกเอง
- `.env` อยู่ใน `.gitignore` ตั้งแต่ commit แรก
- log ผ่าน filter ที่ลบค่าของคีย์ที่มีคำว่า key / secret / token / password / passphrase และที่อยู่แบบ `0x…` ออกอัตโนมัติ
- ตั้งใจ **ไม่** ลบเลขล้วนยาวๆ ออก เพราะ epoch timestamp จะหายไปด้วย
