# 04 · ตัวตัดสินปัจจัยสนับสนุน (Confluence Judge)

## ทำไมต้องใช้ LLM

ปัจจัยสนับสนุนในเอกสารต้นทางเขียนไว้เป็นภาษาคน ไม่ใช่เกณฑ์ตัวเลข:

- "ราคาเบรคทะลุเส้นแนวโน้มกดขึ้นมาได้สำเร็จ"
- "แท่งเทียนแดงขนาดใหญ่ติดกัน 3 แท่งขึ้นไป หรือเกิด gap บ่งชี้ว่ารายย่อยโยนของทิ้งหมดแล้ว"
- "ราคาสร้างจุดต่ำสุดใหม่ที่สูงกว่าจุดต่ำสุดเดิมอย่างชัดเจน"

คำว่า "สำเร็จ", "ขนาดใหญ่", "อย่างชัดเจน" ไม่มีเกณฑ์ตายตัว การเขียนเป็น threshold แข็งๆ คือการแอบตัดสินใจแทนคนออกแบบระบบ จึงเลือกให้ LLM เป็นผู้ตัดสิน แต่ล้อมด้วยข้อจำกัดด้านล่าง

## หก factor — สามต่อฝั่ง

เอกสารต้นทางเขียนไว้ฝั่ง long ฝั่ง short คือภาพสะท้อนของมันทีละข้อ ไม่ใช่ชุดกฎใหม่

| ฝั่ง | factor | ความหมาย |
| --- | --- | --- |
| long | `CHANNEL_BREAKOUT` | เบรคเส้นแนวโน้มกดขึ้นไปได้สำเร็จ |
| long | `RETAIL_CAPITULATION` | รายย่อยโยนของทิ้ง — แท่งแดงใหญ่ติดกัน หรือ gap ลง |
| long | `HIGHER_LOW` | จุดต่ำสุดใหม่สูงกว่าเดิมอย่างชัดเจน |
| short | `CHANNEL_BREAKDOWN` | หลุดเส้นแนวโน้มรับลงมาได้สำเร็จ |
| short | `BUYING_EXHAUSTION` | แรงซื้อหมดแรงที่ยอด — แท่งเขียวใหญ่ติดกัน หรือ gap ขึ้น แล้วไปต่อไม่ได้ |
| short | `LOWER_HIGH` | จุดสูงสุดใหม่ต่ำกว่าเดิมอย่างชัดเจน |

**ตัดสินเฉพาะ factor ของฝั่งที่กำลังจะเข้าเท่านั้น** — สัญญาณ long ถาม 3 ตัวของฝั่ง long ไม่ถามฝั่ง short เลย ไม่มีการหักลบข้ามฝั่ง

## LLM เห็นอะไร

**ตัวเลขเท่านั้น ไม่ใช่ภาพกราฟ** — OHLCV ย้อนหลังพร้อม feature ที่คำนวณมาให้แล้ว:

| Feature | ใช้กับ factor ไหน |
| --- | --- |
| swing low พร้อมดัชนีแท่ง | `HIGHER_LOW` |
| swing high พร้อมดัชนีแท่ง | `LOWER_HIGH` |
| เส้นกรอบแนวโน้มกด (linear fit) และระยะห่างของราคาจากเส้น | `CHANNEL_BREAKOUT` |
| เส้นกรอบแนวโน้มรับ (linear fit) และระยะห่างของราคาจากเส้น | `CHANNEL_BREAKDOWN` |
| ขนาด body เทียบ ATR (z-score) | `RETAIL_CAPITULATION`, `BUYING_EXHAUSTION` |
| ลำดับแท่งแดงติดกัน | `RETAIL_CAPITULATION` |
| ลำดับแท่งเขียวติดกัน | `BUYING_EXHAUSTION` |
| gap ของราคา (มีทิศทาง) | `RETAIL_CAPITULATION`, `BUYING_EXHAUSTION` |

เหตุผลที่ไม่ใช้ภาพ: ทวนสอบได้ยาก แพงกว่า และ reproduce ไม่ได้ ถ้าจะเปลี่ยนไปใช้ภาพในอนาคต ต้องถือเป็นการเปลี่ยนสถาปัตยกรรม ไม่ใช่การสลับ flag

## สัญญาผลลัพธ์ (contract)

หนึ่งคำตัดสินต่อหนึ่ง factor:

```
ConfluenceVerdict {
  factor:        CHANNEL_BREAKOUT | RETAIL_CAPITULATION | HIGHER_LOW
               | CHANNEL_BREAKDOWN | BUYING_EXHAUSTION | LOWER_HIGH
  side:          long | short          ต้องตรงกับฝั่งของ factor
  present:       bool
  confidence:    float 0..1
  evidence_bars: [int]     ดัชนีแท่งที่ใช้อ้างอิง ต้องไม่ว่างเมื่อ present = true
  rationale:     str       ภาษาคน สั้น อ้างถึงแท่งใน evidence_bars
}
```

`confidence` และ `rationale` มีไว้ **ให้คนตรวจย้อนหลัง ไม่ได้เข้าไปในสูตรขนาดไม้** ดู [05](05-position-sizing.md)

## prompt แยกสองชุด

`prompts/long/` และ `prompts/short/` เป็นคนละไฟล์ ไม่ใช่ prompt เดียวที่สลับคำว่า "ซื้อ/ขาย" ด้วย template

เหตุผล: prompt คนละชุดให้ `prompt_hash` คนละค่าโดยธรรมชาติ การแก้ถ้อยคำฝั่ง short จึงไม่ทำให้ cache ของฝั่ง long เสียไปด้วย

## ข้อบังคับเรื่องความคงเส้นคงวา

เอกสารต้นทางยืนอยู่บนหลักที่ว่า "ระบบไม่เคยหลอกเรา" ระบบที่ตอบคนละอย่างสองครั้งบนข้อมูลชุดเดิมถือว่าหลอก จึงบังคับ:

1. **บังคับ structured output** — ส่ง schema เข้าพารามิเตอร์ของปลายทาง (`response_format.json_schema` ของ endpoint แบบ OpenAI-compatible) **ไม่ใช่แปะ schema ลง prompt แล้วขอร้อง** · และตั้งค่าการสุ่มให้ต่ำสุดเท่าที่ API นั้นรองรับ (`temperature 0` ถ้ามี ไม่รับก็ไม่ต้องส่ง) — ค่านี้**ลด**การแกว่ง ไม่ได้**กำจัด** เพราะ endpoint ที่ทำ batching รวมผลบวกทศนิยมคนละลำดับตามองค์ประกอบของ batch พอ logit ขยับ greedy ก็เลือกคนละ token ได้ · ตัวที่รับประกันจริงคือข้อ 2 · ผู้ให้บริการที่รูปคำขอไม่ใช่แบบนี้ถือเป็นการเปลี่ยน adapter ไม่ใช่การสลับ flag
2. **cache ต่อแท่ง** — key คือ `(market, symbol, timeframe, bar_close_ts, side, factor, prompt_hash)` ตัดสินครั้งเดียวจบ เรียกซ้ำได้คำตอบเดิมเสมอ · `market` อยู่ในคีย์เพราะ ADR 26 ทำให้มันเป็นมิติของ symbol — `BTC/USDT` บน spot กับบน perp เป็นคนละแท่งจริงๆ คำตัดสินที่คำนวณจากแท่งคนละชุดจึงทับกันไม่ได้
3. `side` อยู่ใน key เพราะมันอยู่ใน PK คู่กับ CHECK ที่ผูก factor↔side — **ไม่ใช่** เพราะคำตัดสินสองฝั่งจะทับกัน · ชื่อ factor ของสองฝั่งไม่ซ้ำกันเลยสักตัว มันจึงทับกันไม่ได้อยู่แล้ว (พิสูจน์ด้วย mutation: ถอด `side` ออกจาก WHERE แล้วเทสต์ทั้งชุดยังเขียว) · ด่านที่จะดังถ้าวันหนึ่งมีชื่อซ้ำคือ `test_the_factor_sets_of_the_two_sides_never_overlap`
4. `prompt_hash` อยู่ใน key เพื่อให้การแก้ prompt ทำให้ cache เก่าใช้ไม่ได้โดยอัตโนมัติ — ไม่ใช่ปนกันเงียบๆ · **hash รวมตัวตนของโมเดลไว้ด้วย** (ชื่อโมเดล บวก host ของ gateway เมื่อปลายทางเป็น endpoint ภายนอก เพราะชื่อโมเดลเดียวกันบน gateway คนละตัวเป็นคนละ quantization ได้) เพราะการเปลี่ยนโมเดลมีผลต่อคำตอบไม่น้อยกว่าการแก้ถ้อยคำ
5. ทุก verdict ถูกเขียนลง `DecisionRecord` ไม่ว่าผลจะเป็นอะไร

## เมื่อ LLM ใช้การไม่ได้

timeout, rate limit, หรือตอบผิด schema → **ถือว่าไม่มีปัจจัยสนับสนุนใดเลย แล้วเข้าไม้ที่ `base_pct`**

เหตุผล: สัญญาณเป็น deterministic อยู่แล้วและไม่ได้พึ่ง LLM กรณีนี้จึงตรงกับ "สัญญาณพื้นฐานที่ไม่มีปัจจัยสนับสนุน" ในตารางของเอกสารต้นทางพอดี — ซึ่งเอกสารบอกให้ลงปริมาณน้อยที่สุดเพื่อทดลองแนวโน้ม

การข้ามสัญญาณไปเลยจะทำให้ความเสถียรของผู้ให้บริการ LLM กลายเป็นตัวแปรของกลยุทธ์ ซึ่งไม่ควรเป็น

**ต้อง log ให้ชัดว่าไม้นี้ลงด้วย fallback ไม่ใช่ด้วยคำตัดสินจริง** ไม่งั้นตอนอ่านย้อนหลังจะแยกไม่ออกระหว่าง "LLM บอกว่าไม่มีปัจจัย" กับ "LLM ตอบไม่ได้"

**ข้อยกเว้น:** ขาปิดของ flip ไม่เรียก Judge เลย — การปิดไม่ต้องการขนาดไม้ ปิดคือปิดทั้งหมดเสมอ ความล้มเหลวของ LLM จึงไม่มีวันขวางการปิดสถานะ
