# 10 · engine lifecycle และสัญญาของ API

[08](08-runtime-pipeline.md) อธิบายว่าเกิดอะไรขึ้น **ในหนึ่งรอบ** ของการปิดแท่ง
หน้านี้อธิบายสิ่งที่อยู่รอบรอบนั้น: ใครสตาร์ทมัน มันหยุดเมื่อไหร่ อะไรอยู่รอดข้ามการรีสตาร์ท
และคอนโซลถามอะไรได้ด้วย endpoint ไหน · สิทธิ์ของแต่ละ endpoint อยู่ที่

ถอดจาก design handoff (การ์ด PROFILE และปุ่ม engine) แล้วปิดช่องที่ design เว้นไว้

> **errata ของใบงาน** — คำบรรยายงานนี้เขียนไว้ว่า state อยู่ในไฟล์
> `var/state/{profile}.json` และ `var/state/killswitch.json` · [decisions.md ข้อ 22](../decisions.md)

> เหตุผลที่ตรงกว่าการอ้างมติ: engine แต่ละ profile เป็น **คนละ process** กับคอนโซล
> state ที่สองฝ่ายเขียนคือของที่ต้องมีการล็อก ซึ่ง DB ทำอยู่แล้วและไฟล์ JSON ไม่ทำ

## 1. หนึ่ง engine ต่อหนึ่ง profile

`live` กับ `paper` เป็น **subprocess แยกกัน** และเดินพร้อมกันได้ · ตัวที่สตาร์ท/หยุด/ดูสถานะ
คือ supervisor ที่อยู่ในกระบวนการของคอนโซล

**engine พังต้องไม่ลากคอนโซลตาย** เป็นเหตุผลทั้งหมดที่มันเป็น subprocess ไม่ใช่ thread:
คอนโซลคือที่เดียวที่คนกด kill switch ได้ ถ้ามันตายไปพร้อม engine เครื่องมือหยุดฉุกเฉิน
ก็หายไปตอนที่ต้องใช้มันที่สุด

**engine ที่พังจะไม่ถูกสตาร์ทใหม่อัตโนมัติ** — มันค้างที่สถานะ `crashed` ให้คนเห็นและกดเอง
สิ่งที่ทำให้มันตายรอบแรก (config ที่พา, venue ล่ม, บั๊ก) ยังอยู่ที่เดิม การปลุกคืนอัตโนมัติ
จึงเปลี่ยนความล้มเหลวที่มองเห็นให้เป็นลูปที่ไม่มีใครเห็น — และเปลี่ยนตอนที่ควรมีคนอ่าน log
ให้เป็นตอนที่ไม่มีใครรู้ว่าต้องอ่าน · การกันออเดอร์ซ้ำไม่ใช่เหตุผลของข้อนี้ `clientOrderId`
กันไว้แล้ว ([06](06-risk-and-execution.md))

## 2. สาม state ที่คนละเรื่องกัน

สับสนสามตัวนี้เมื่อไหร่จะได้ปุ่มที่โกหกหน้าจอ

| state | เจ้าของ | อยู่รอดข้าม | ปลดด้วย |
| --- | --- | --- | --- |
| `engine.should_run` | คอนโซล (เจตนา) | รีสตาร์ทเครื่อง | `engine/start` · `engine/stop` |
| `engine.observed` | supervisor (ความจริง) | — คิดใหม่ทุกครั้งที่ถาม | — |
| `kill_switch.latched` | ใครก็กดได้ (ดู [09](09-users-and-auth.md)) | รีสตาร์ท engine **และ** รีสตาร์ทเครื่อง | `killswitch/unlatch` เท่านั้น |

**การปลดมีสามด่านซ้อนกัน ไม่ใช่ด่านเดียว** — พิมพ์ชื่อ profile ยืนยัน
([06](06-risk-and-execution.md)) · เป็น `OWNER` · และ step-up TOTP
([09](09-users-and-auth.md)) · ด่านแรกกันการกดผิดโปรไฟล์ สองด่านหลังกันการกดผิดคน
ทั้งสามอย่างตอบคำถามคนละข้อ จึงไม่มีข้อไหนแทนกันได้

### `engine.running` ไม่ใช่ค่าเดียว มันเป็นสองค่า

design วาดปุ่มเดียวกับป้าย `engine live · running` ซึ่งอ่านได้ว่า "running" เป็นค่าเดียว
**มันไม่ใช่** — เจตนาของคน (`should_run`) กับสภาพจริงของ process (`observed`) แยกกันได้
และตอนที่มันแยกกันคือตอนที่สำคัญที่สุด: engine ตายไปเมื่อสิบนาทีก่อนแต่หน้าจอยังเขียนว่า
`running` คือการโกหกที่ทำให้ไม่มีใครไปกดสตาร์ท

ในตารางเก็บ **เจตนา** กับ **heartbeat** (`last_heartbeat_ts` ที่ engine เขียนทุกครั้งที่วนรอบ)
· `/api/engine/status` คืนทั้งสองอย่างและคำนวณสถานะที่แสดงจากทั้งคู่:

| `should_run` | heartbeat | สถานะที่แสดง |
| --- | --- | --- |
| `false` | เก่า/ไม่มี | `stopped` |
| `true` | สดกว่าสองรอบ heartbeat | `running` |
| `true` | เก่ากว่านั้น | **`crashed`** |
| `false` | สด | `stopping` (สั่งหยุดแล้วยังปิดตัวไม่เสร็จ) |

### `engine.should_run` ≠ `kill_switch.latched`

สอง state คนละตัว คนละ endpoint และ **ไม่มีทางที่ตัวหนึ่งไปเปลี่ยนอีกตัว**:

- **start/stop engine ไม่ปลด kill switch** — สตาร์ท engine ตอนที่ kill switch ยัง latched
  ได้ตามปกติ engine จะขึ้นมา อ่านสถานะ รายงาน แต่ **ไม่เปิดไม้ใหม่** จนกว่าจะมีคนปลด
  ถ้าการสตาร์ทปลด latch ไปด้วย คำว่า latched ก็ไม่มีความหมาย เพราะทางออกจากมัน
  จะเป็นการกดสองปุ่มที่ไม่มีใครตั้งใจให้เป็นการปลด
- **kill switch ไม่หยุด process** — latch แล้ว engine ยังเดินอยู่ ยังบันทึกการตัดสินใจ
  ที่ลงท้ายด้วยเหตุผลว่าถูก kill switch กั้น ([08](08-runtime-pipeline.md) ขั้น 14)
  ประวัติที่ขาดหายไปตอนฉุกเฉินคือประวัติที่ขาดหายไปตรงที่อยากอ่านที่สุด

**หยุด engine ไม่ใช่ปิดไม้** — ไม้ที่เปิดอยู่ยังอยู่ที่ venue ต่อไป และ stop loss ที่วางไว้
ที่ exchange ([decisions.md ข้อ 17](../decisions.md)) ยังทำงานอยู่ · การปิดไม้เป็น action
ของคนอีกอันหนึ่ง (`close_position_manual`) ปุ่มที่หยุดบอทแล้วปิดไม้ให้ด้วยคือปุ่มที่คนกด
ตอนตกใจแล้วเสียใจตอนเช้า

## 3. สลับโหมดไม่ใช่การควบคุม

**โหมดคือมุมมอง** — `POST /api/session/mode` เปลี่ยนว่า session นี้กำลังดูโปรไฟล์ไหน
และ **ต้องไม่แตะ engine ตัวใดเลย** ไม่ start ไม่ stop ไม่ pause

engine สองตัวเป็น state อิสระที่เดินต่อขณะที่คนสลับไปมาดู · คนที่ปิดแท็บไปแล้วกลับมา
ต้องเจอ engine อยู่ในสภาพเดิม ไม่ใช่สภาพที่ขึ้นกับว่าใครดูหน้าไหนอยู่ก่อนหน้า

การสลับไป `live` ต้อง step-up TOTP ([09](09-users-and-auth.md)) · สลับกลับ `paper` ไม่ต้อง

## 4. รอบชีวิตของ engine

```
start  →  [ วนรอบ: รอแท่งปิด → อ่าน config → อ่านสถานะจริงจาก venue → ตัดสินใจ → บันทึก ]  →  stop
```

**ไม่มีขั้น reconcile พิเศษตอนสตาร์ท** — [06](06-risk-and-execution.md) บังคับให้
อ่าน `positions()` และ `open_orders()` จากปลายทาง **ก่อนตัดสินใจทุกครั้ง** ห้ามเชื่อสถานะ
ที่จำไว้ อยู่แล้ว · รอบแรกหลังสตาร์ทจึงเป็นการอ่านนั้นเอง ไม่ใช่ขั้นตอนที่สองที่ต้องดูแลแยก
· ของที่ค้างจากการตายกลางทางถูกเจอที่นั่น และ `clientOrderId` ที่คำนวณแบบ deterministic
กันการส่งซ้ำในแท่งเดิมไว้อีกชั้น

**อ่าน config ใหม่ทุกต้นรอบ ไม่ใช่ตอนสตาร์ทครั้งเดียว** — คอนโซลแก้ config เป็นเวอร์ชันใหม่
แล้วเลื่อนตัวชี้ ([decisions.md ข้อ 18](../decisions.md)) engine จึงเห็นของใหม่ที่ต้นรอบถัดไป
โดยไม่ต้องรีสตาร์ท · **รอบที่กำลังเดินอยู่ใช้เวอร์ชันเดิมจนจบรอบ** ไม่อ่านกลางทาง เพราะ
การตัดสินใจหนึ่งครั้งต้องอ้าง `config_version_id` เดียว ไม่ใช่สองค่าที่คาบเกี่ยวกัน

**config ที่ validate ไม่ผ่าน = หยุดเทรดทั้ง profile ไม่ใช่แค่คู่ที่แก้** — engine เข้าสถานะ
`blocked` บันทึกว่าติดข้อไหน แล้ววนรอบต่อไปโดยไม่เทรด · **ไม่ exit** เพราะ process ที่ตายแล้ว
บอกไม่ได้ว่าตายเพราะอะไร และคอนโซลจะแสดงได้แค่ `crashed` ซึ่งชี้ไปผิดที่

**ตอนหยุด** — จบรอบที่กำลังทำอยู่ก่อนแล้วปิดตัว ไม่ตัดกลางการส่งออเดอร์ · ระหว่างนั้น
สถานะที่แสดงคือ `stopping`

## 5. state ที่อยู่ในตาราง

| ตาราง | คอลัมน์ | ใครเขียน |
| --- | --- | --- |
| `engine_state` | `profile` (PK) · `should_run` · `last_heartbeat_ts` · `blocked_reason` | คอนโซลเขียนเจตนา · engine เขียน heartbeat กับ `blocked_reason` |
| `kill_switch` | `profile` (PK) · `latched` · `latched_by` · `latched_ts` · `reason` | คอนโซล |

**สองตารางนี้เขียนทับได้ (`UPDATE`) ต่างจากตารางข้อเท็จจริง** ([decisions.md ข้อ 23](../decisions.md))
เพราะมันคือ *สภาพปัจจุบัน* ไม่ใช่ *สิ่งที่เกิดขึ้น* · ประวัติของการกด kill switch ใครกดเมื่อไหร่
อยู่ที่ `user_audit_log` ([09](09-users-and-auth.md)) ซึ่งแก้ไม่ได้ — สภาพอ่านจากตารางเดียว
ประวัติอ่านจากตารางที่ไม่มีใครลบได้ อย่าเอาสองหน้าที่นี้มาไว้ที่เดียวกัน

**ไม่มี `cold_start_done`** — cold start เป็นเรื่องของ **แต่ละรอบการรัน** ไม่ใช่ธงที่ติดอยู่
กับ profile ตลอดกาล ([03](03-trading-rules.md)) ธงแบบนั้นจะทำให้บอทที่รีสตาร์ทหลังหยุดไป
สามวันคิดว่าตัวเองไม่ได้เพิ่งเปิดขึ้นมา ซึ่งเป็นเวลาที่มันเพิ่งเปิดขึ้นมาที่สุด

### `daily_loss` และ `consecutive_losses` **ไม่ใช่ state** และไม่มีตารางของตัวเอง

คำบรรยายใบงานเขียนไว้ว่า state ต่อ profile เก็บสองค่านี้ด้วย — **ทำไม่ได้**
[decisions.md ข้อ 24](../decisions.md) ระบุ "จำนวนไม้ที่แพ้ติดกัน" ไว้ตรงตัวว่าเป็น **VIEW
ห้ามเก็บเป็นตาราง** เพราะตารางสรุปคือแหล่งความจริงที่สองที่จะขัดกับแหล่งแรกในวันที่มีบั๊ก

- **แพ้ติดกัน** — VIEW บน `trades`/`fills`
- **ขาดทุนวันนี้** — VIEW ให้ **ส่วนที่รับรู้แล้ว** ส่วนตัวตัดสิน risk เป็น**ฟังก์ชันที่รับ
  mark price เข้ามา** เพราะ [06](06-risk-and-execution.md) บังคับให้นับกำไรขาดทุนที่ยังไม่ปิด
  ด้วย และ mark price สดไม่มีอยู่ในตารางไหนเลย (ข้อยกเว้นที่ ADR 24 เขียนไว้เอง)

ขอบวันเป็นเที่ยงคืน UTC ([06](06-risk-and-execution.md)) ซึ่งเป็นเงื่อนไขของ **query**
ไม่ใช่ตัวนับที่ต้องมีใครไปล้าง · ตัวนับที่ต้องมีใครไปล้างตอนเที่ยงคืนคืองานที่มีวันลืม
และคอนโซลกับ engine จะอ่านได้ไม่ตรงกันในนาทีที่คาบเกี่ยว

## 6. สัญญาของ API

ทุก endpoint ต้องมี session ที่ผ่านสองขั้นแล้ว ([09](09-users-and-auth.md)) ·
`{profile}` เป็น `live` หรือ `paper` เท่านั้น ค่าอื่นคือ 404 ไม่ใช่ 400 —
โปรไฟล์ที่ไม่มีอยู่ไม่ใช่คำขอที่ผิดรูป

### อ่าน

| endpoint | คืนอะไร |
| --- | --- |
| `GET /api/{profile}/overview` | โซนและสัญญาณต่อ symbol · สถานะไม้ · margin/notional ต่อฝั่ง · ขาดทุนวันนี้เทียบเพดาน · ตัวนับ breaker |
| `GET /api/{profile}/risk` | risk limit ของเวอร์ชันที่ active · สถานะ kill switch · leverage และราคา liquidation ต่อเหรียญ |
| `GET /api/{profile}/records` | บันทึกการตัดสินใจ paginate + filter (ฝั่ง, flip, risk, fallback, เพดาน) |
| `GET /api/{profile}/config` | เวอร์ชันที่ active + ผล validate ต่อฟิลด์ |
| `GET /api/config/diff?from=&to=` | ผลต่างระหว่างสองเวอร์ชันของ config **ทีละฟิลด์** |
| `GET /api/{profile}/records/export` | บันทึกทั้งหมดเป็นไฟล์ — ผ่าน redaction ตัวเดียวกับ log |
| `GET /api/engine/status` | **ทั้งสอง profile ในคำขอเดียว** — `should_run` · heartbeat · สถานะที่คำนวณแล้ว · `blocked_reason` |

`/api/engine/status` คืนทั้งสอง profile เสมอ ไม่ใช่ต่อ profile เพราะการ์ด PROFILE
แสดงสถานะของอีกโหมดอยู่ด้วย (`paper: running`) ถ้าแยกเป็นสอง endpoint หน้าเดียวต้องยิงสองครั้ง
แล้วได้ภาพที่ต่างเวลากันเล็กน้อยทุกครั้ง

### เขียน

| endpoint | ผล | ทำซ้ำแล้วเป็นอย่างไร |
| --- | --- | --- |
| `POST /api/{profile}/engine/start` | ตั้ง `should_run = true` แล้วให้ supervisor สตาร์ท | สตาร์ทซ้ำตอนที่ heartbeat ยังสด = **no-op คืน 200** ไม่ใช่ error |
| `POST /api/{profile}/engine/stop` | ตั้ง `should_run = false` | no-op คืน 200 |
| `POST /api/{profile}/killswitch/latch` | `latched = true` พร้อมคนกดและเหตุ | no-op คืน 200 — **การกดหยุดฉุกเฉินซ้ำต้องไม่เคยล้มเหลว** |
| `POST /api/{profile}/killswitch/unlatch` | `latched = false` | no-op คืน 200 |
| `POST /api/session/mode` | เปลี่ยนโหมดที่ session นี้ดู · **ไม่แตะ engine** | idempotent |
| `POST /api/{profile}/config` | สร้าง **เวอร์ชันใหม่** แล้วเลื่อนตัวชี้ ([ข้อ 18](../decisions.md)) | สร้างเวอร์ชันใหม่อีกใบที่เนื้อเหมือนกัน — ไม่ใช่ error |
| `POST /api/{profile}/config/dry_run` | เวอร์ชันใหม่ที่ต่างกันฟิลด์เดียว — แยก endpoint เพราะสิทธิ์ต่างกัน | เวอร์ชันใหม่ที่เนื้อเหมือนกัน |
| `POST /api/{profile}/symbols` · `DELETE /api/{profile}/symbols/{symbol}` | เวอร์ชันใหม่ที่บล็อก `[[symbols]]` ต่างไป | เวอร์ชันใหม่ที่เนื้อเหมือนกัน |
| `POST /api/{profile}/positions/{symbol}/close` | ปิดไม้ฉุกเฉิน — **ไม่แตะ engine และไม่แตะ kill switch** | **ไม่ idempotent** — ปิดไม้ที่ปิดแล้วคืน 409 ไม่ใช่ 200 |
| `POST /api/{profile}/coldstart/{symbol}` | เลือกเส้นทาง cold start ของรอบนี้ ([03](03-trading-rules.md)) | เลือกซ้ำค่าเดิม = no-op · เลือกค่าใหม่ = ทับเจตนาเดิมได้จนกว่ารอบจะเดิน |
| `POST /api/users` · `/users/{id}/role` · `/suspend` · `/unlock` · `/permissions` · `POST /api/users/{id}/reset-2fa` · `DELETE /api/sessions/{id}` | จัดการผู้ใช้ ([09](09-users-and-auth.md)) | ตามความหมายของแต่ละตัว — ดู [09](09-users-and-auth.md) |

**หน้านี้เป็นรายการ endpoint ที่ถือเป็นจริง** ([09](09-users-and-auth.md) ผูกสิทธิ์ให้แต่ละตัว
แต่ไม่ได้นิยาม URL) endpoint ใหม่ต้องเพิ่มที่นี่**และ**ที่ตารางสิทธิ์พร้อมกัน อันไหนขาดไป
ตัวตรวจสิทธิ์จะไม่มีแถวให้เทียบและต้องคืน 403

**ปิดไม้ฉุกเฉินไม่ idempotent โดยเจตนา** — ต่างจากการหยุด: คนที่กดปิดไม้ซ้ำแล้วได้ 200
จะเข้าใจว่าปิดไปสองครั้งสำเร็จ ทั้งที่ครั้งที่สองไม่มีไม้ให้ปิด · 409 บอกความจริงว่า
"ไม่มีอะไรให้ทำแล้ว" ซึ่งเป็นคำตอบที่ต่างจาก "ทำสำเร็จ"

**การหยุดต้องกดซ้ำได้เสมอ** เป็นข้อบังคับ ไม่ใช่ความสะดวก: คนที่กด latch แล้วเห็น error
เพราะมันถูก latch อยู่แล้ว จะไม่รู้ว่าตัวเองหยุดสำเร็จหรือยัง แล้วจะไปกดอย่างอื่น

**`POST /api/{profile}/config` ไม่ใช่ `PUT`** เพราะมันไม่ทับของเดิม มันสร้างของใหม่

## 7. เกณฑ์ยืนยันความถูกต้อง

1. `POST engine/stop` แล้ว **ไม้ที่เปิดอยู่ยังอยู่** และ stop loss ที่ venue ยังอยู่
2. `POST engine/start` ตอนที่ `kill_switch.latched = true` → engine ขึ้น **แต่ไม่เปิดไม้ใหม่**
   และ latch ยังเป็น `true`
3. `POST session/mode` **ไม่เปลี่ยน `should_run` ของ profile ใดเลย**
4. ฆ่า process ของ engine ทิ้ง → `GET /api/engine/status` เปลี่ยนเป็น `crashed`
   ภายในสองรอบ heartbeat **และไม่มีการสตาร์ทใหม่เอง**
5. เลื่อนตัวชี้ config ไปเวอร์ชันที่ validate ไม่ผ่าน → engine เข้า `blocked`
   **ไม่เทรดทั้ง profile** และ process **ยังอยู่**
6. latch ซ้ำสองครั้ง → 200 ทั้งสองครั้ง
7. รีสตาร์ท engine ขณะ latched → latch **ยังอยู่**
8. `GET /api/engine/status` คืนทั้งสอง profile ในคำขอเดียว
9. ไม่มีตารางไหนเก็บ `daily_loss` หรือ `consecutive_losses` — เลขที่คอนโซลแสดง
   มาจาก VIEW กับฟังก์ชันที่รับ mark price ([decisions.md ข้อ 24](../decisions.md))
