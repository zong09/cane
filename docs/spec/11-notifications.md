# 11 · การแจ้งเตือน

> ไฟล์ `09` และ `10` จองไว้ให้สเปกผู้ใช้/auth และ engine lifecycle ตามลำดับ

ระบบยิงออเดอร์เองโดยไม่มีคนกดยืนยันต่อไม้ ([06](06-risk-and-execution.md)) การแจ้งเตือนจึงไม่ใช่ของประดับ — มันคือช่องทางเดียวที่คนรู้ว่าระบบทำอะไรไปโดยไม่ต้องเปิดคอนโซลค้างไว้

## เกิดที่ engine ไม่ใช่ที่คอนโซล

event เกือบทั้งหมดเกิดตอน engine ทำงาน คอนโซลเป็นแค่ที่แสดงผลกับที่ตั้งค่า ([decisions #21](../decisions.md)) ผลคือ **เฟสบอทต้องส่งแจ้งเตือนได้ตั้งแต่ยังไม่มีคอนโซล** ไม่งั้นช่วง paper run ทั้งช่วงจะต้องนั่งเฝ้า log เอง

## ชนิดของ event

| ชนิด | ระดับ | ตัวอย่างเนื้อหา |
| --- | --- | --- |
| **ส่งคำสั่ง** | เสี่ยง/ยิงจริง | `ส่งคำสั่ง long BTC/USDT 45%` · `fill 58,465 · margin 45.00 · notional 90.00` |
| **flip ไม่สำเร็จ** | เสี่ยง/ยิงจริง | `flip_aborted` พร้อม `residual_qty` — มีสถานะค้างที่คนต้องไปปิดเอง ([03](03-trading-rules.md)) |
| **ไม้ที่ถืออยู่ขาดทุนหนัก** | เสี่ยง | `SOL/USDT ขาดทุน -11.0%` · `มาร์จิ้น -22.1% · liq 83.53` |
| **risk limit ทำงาน** | เสี่ยง | kill switch latch · daily loss ชนเพดาน |
| **config โหลดไม่ผ่าน** | เตือน | `live.toml โหลดไม่ผ่าน 4 ข้อ` พร้อมชื่อคีย์ ([07](07-data-and-config.md)) |
| **auth** | ข้อมูล | เข้าสู่ระบบ · เปลี่ยนสิทธิ์ · เพิกถอน session |
| **ปิดแท่งรายวัน** | สรุป | `ประมวลผลครบ 4 symbol · สัญญาณรอดำเนินการ 2 · ไม้ที่ถืออยู่ 2` |

ทุก event ผูกกับ **โหมด** (`live` / `paper`) เสมอ

### เกณฑ์ของ "ขาดทุนหนัก"

`min_liq_buffer_pct` กันตอน**เปิด**ไม้ และ `max_daily_loss_pct` นับทั้งพอร์ต — ไม่มีตัวไหนเฝ้าไม้ที่เปิดค้างอยู่รายตัว จึงเพิ่ม `alert_position_loss_pct` ในการตั้งค่าการแจ้งเตือน

**ไม่ระบุ = ไม่เตือน** (fail-closed ในทางที่ไม่รบกวน) — ต่างจาก risk limit ตรงที่ตัวนี้ไม่ได้ห้ามอะไร มันแค่บอก ระบบจึงเดินต่อได้โดยไม่มีมัน แต่ต้องไม่เดาเกณฑ์ให้เอง

## ช่องทาง

LINE (Messaging API) และ Telegram (Bot API)

**สวิตช์เปิดปิดแยก (ช่องทาง × โหมด)** — สี่สวิตช์อิสระ ปิด paper ไว้เพื่อไม่ให้เสียงเตือนจากการทดลองปนกับไม้จริงได้ โดยไม่กระทบ live

```
notifications
  line     { live: bool, paper: bool }
  telegram { live: bool, paper: bool }
```

**การส่งทุกครั้งต้องเช็คสวิตช์ของโหมดที่ยิง ไม่ใช่โหมดที่คนกำลังดูอยู่** — engine paper ที่ปิด LINE ไว้ต้องไม่ยิงเข้ากลุ่มจริง ข้อนี้เป็นจุดที่พลาดแล้วสร้างความสับสนว่าไม้จำลองเป็นไม้จริง

สวิตช์เก็บที่ `var/state/notifications.json` **ไม่ใช่ในไฟล์ profile** เพราะมันคุมทั้งสองโหมดพร้อมกันและเป็น state ของการทำงาน ไม่ใช่ค่าตั้งต้นของกลยุทธ์ ([decisions #18](../decisions.md))

## credential

คีย์เป็น **ชุดเดียวต่อช่องทาง ใช้ร่วมทั้งสองโหมด** แยกกันเฉพาะสวิตช์ ถ้าจะให้บอทคนละตัวต่อโหมด ต้องแยก credential เป็นรายโหมดด้วย ซึ่งถือเป็นการเปลี่ยน schema

| ช่องทาง | env var | ความลับ |
| --- | --- | --- |
| LINE | `CANE_LINE_TOKEN` | ✓ |
| LINE | `CANE_LINE_SECRET` | ✓ |
| LINE | `CANE_LINE_TO` (group / room / user id) | — |
| Telegram | `CANE_TELEGRAM_TOKEN` | ✓ |
| Telegram | `CANE_TELEGRAM_CHAT_ID` | — |
| Telegram | `CANE_TELEGRAM_THREAD_ID` (ถ้าใช้ topic) | — |

อยู่ใน `.env` ตาม pattern เดิม ([06](06-risk-and-execution.md)) — ชื่อทั้งสามตัวที่เป็นความลับมีคำว่า `TOKEN` / `SECRET` จึงเข้าเกณฑ์ตัวกรอง log อยู่แล้วโดยไม่ต้องเพิ่มกฎ

**ข้อบังคับตอนแสดงค่า:** คอนโซลอ่านกลับมาแสดงเป็นค่าปิดบังเสมอ การกด "แสดงค่า" ต้องเป็นการเรียกที่ **บันทึก audit log** และการบันทึกคีย์ที่กระทบโหมด live ต้องผ่าน 2FA step-up — บังคับที่ endpoint ไม่ใช่ที่หน้าจอ

## LINE webhook ขาเข้า

LINE Messaging API ต้องมี endpoint สาธารณะรับ callback (`POST /hooks/line/{id}`) นี่คือ **จุดเดียวของทั้งระบบที่เปิดรับ request จากอินเทอร์เน็ต** จึงต้อง

- ตรวจลายเซ็นด้วย `CANE_LINE_SECRET` ทุก request ตรวจไม่ผ่าน = ทิ้ง ไม่ตอบรายละเอียด
- ไม่มีเส้นทางจาก webhook นี้ไปถึงการยิงออเดอร์ **ไม่ว่ากรณีใด** — ข้อความขาเข้าใช้ได้อย่างมากแค่ยืนยันว่าบอทอยู่ในกลุ่ม
- `{id}` เป็นค่าสุ่มต่อการติดตั้ง ไม่ใช่ค่าที่เดาได้

## สิ่งที่ยังไม่ทำในเฟสนี้

UI ทั้งหมด (กระดิ่ง แผงรายการ ฟอร์มคีย์) เป็นงานเฟสคอนโซล เฟสบอทต้องการแค่ตัวส่งกับสวิตช์ที่อ่านจาก state ได้
