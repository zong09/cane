# ADR 35 · เลือกเส้นทาง cold start ต่อเหรียญเป็นเจตนาของรอบถัดไป

**สถานะ:** accepted (2026-09-23) · **ยังไม่มีโค้ด** — `POST /api/{profile}/coldstart/{symbol}` ใน
[spec/10 §6. สัญญาของ API](../spec/10-engine-and-console.md) ยังติดป้ายว่ายังไม่สร้างจนกว่าใบที่ทำข้อนี้จะเสร็จ

ใบ 25 สร้างแท็บ Cold start แบบอ่านอย่างเดียว · เส้นทางวันนี้มาจาก `cold_start` ของ config ซึ่ง
เป็นค่าเดียวต่อโปรไฟล์ แต่ design (§9.2c) กับ spec/10 ให้คนเลือกต่อเหรียญต่อรอบ และ spec/03
§การเลือกเส้นทาง เขียนไว้ว่า "เมื่อถึงเฟสคอนโซลค่อยเปลี่ยนเป็นให้คนเลือกในหน้าจอ"

## ข้อจำกัดที่ข้อเสนอนี้ต้องเคารพ

1. **ห้ามมีธง `cold_start_done` บนดิสก์** (spec/03 §เกิดใหม่ทุกครั้งที่ start engine) — ทุกครั้งที่
   engine เริ่มคือ cold start ครั้งใหม่
2. **engine ตัดสินแท่งแรกทันทีที่เริ่ม** — `loop.run()` เริ่มด้วย `done_close = 0` แล้ว
   `due_close()` คืนแท่งที่ปิดล่าสุดในรอบแรกเลย · ไม่มีช่วงหลัง start ให้คนเลือก
   **เจตนาจึงต้องถูกเลือกก่อนกด start** และต้องผูกกับ run ที่จะเกิด ไม่ใช่ run ที่กำลังเดิน
3. **ตัวกันจริงยังเป็น "ไม่มีสถานะเปิดทั้งสองฝั่ง"** (spec/03 §เงื่อนไขบังคับ) · เจตนาเลือกได้แค่
   *ทาง* — ไม่ข้ามประตูใดของ `late_entry()` · ทาง `trailing` ยังต้องมี stop และ RR ≥ 2:1
4. **เป็นตารางสภาพ ไม่ใช่ตารางข้อเท็จจริง** (ADR 23) — แบบเดียวกับ `kill_switch` ·
   ประวัติว่าใครเลือกอะไรอยู่ที่ `user_audit_log` ส่วนทางที่ใช้จริงอยู่ที่ `decisions.cold_start`

## กลไก — เจตนาถูก**ใช้แล้วหายไป** ไม่ใช่หมดอายุตามเวลา

ตาราง `cold_start_intent` · กุญแจ `(profile, market, symbol)` · คอลัมน์ `route`
(`trailing` / `skip`), `chosen_by`, `chosen_ts` · คอนโซล `INSERT … ON CONFLICT UPDATE`
(เลือกซ้ำค่าเดิม = no-op, เลือกค่าใหม่ = ทับ — ตามคอลัมน์ "ทำซ้ำแล้วเป็นอย่างไร" ของ spec/10)

engine ที่**แท่งแรกของ run ของเหรียญนั้น** (`SymbolRuntime.cold_start_pending` ที่มีอยู่แล้วและ
ตั้งใจให้อยู่ในหน่วยความจำ) อ่านแถวนั้น · มีแถว = ใช้ `route` ของแถวแทน `cold_start` ของ config ·
แล้ว **`DELETE` แถวนั้นในทรานแซกชันเดียวกับที่เขียนแถว `decisions`** — เจตนาถูกใช้ครั้งเดียว
โดย run ที่ใช้มันจริงเท่านั้น · ไม่มีแถว = ใช้ config ตามเดิม ซึ่งคือพฤติกรรมของวันนี้

ใช้แล้วหายไปแม้แท่งแรกจะไม่ใช่สถานการณ์ตกรถ (เป็นแท่งสัญญาณ หรือถือไม้อยู่) — เจตนาคือ
"สำหรับ run ถัดไป" และ run นั้นผ่านโอกาส cold start ของมันไปแล้ว · ถ้าให้ค้างไว้ มันจะไปโผล่ใน
run ที่คนไม่ได้ตั้งใจ

**ทำไมไม่ใช้เวลา** (ร่างแรกของข้อนี้): ผูกอายุกับเวลาเริ่ม run ต้องรู้ว่า run ก่อนหน้าเริ่มเมื่อไหร่ ·
`decisions.cold_start` ถูกเขียนเฉพาะแท่งที่เข้าประตู `cane_rule` จึงใช้แยก run ไม่ได้ — run ที่เริ่มที่
แท่งสัญญาณไม่ทิ้งร่องรอย แล้วเจตนาเก่าจะค้างข้าม run · การใช้แล้วลบไม่มีกรณีกำกวมเลย

**engine ได้ `SELECT, DELETE` ไม่ได้ `INSERT`/`UPDATE`** — engine เลือกเส้นทางแทนคนไม่ได้ ·
คอนโซลได้ `SELECT, INSERT, UPDATE` ไม่ได้ `DELETE` — การยกเลิกเจตนาคือการเลือกใหม่ ไม่ใช่การลบ
ร่องรอย · replay ไม่อ่านตารางนี้ (scratch DB ไม่มีเจตนา และ replay คือประวัติ ไม่ใช่ run ถัดไป)

แถว `decisions` ของแท่งนั้นบันทึก `cold_start` เป็นทางที่ใช้จริงอยู่แล้ว · **ไม่เพิ่มคอลัมน์แหล่งที่มา**
(config หรือคน) — คนที่เลือกอยู่ที่ `user_audit_log` ซึ่งลบไม่ได้ แหล่งที่สองคือของซ้ำ

สิทธิ์ `choose_cold_start_route` (OWNER, TRADER) มีอยู่แล้วในตารางสิทธิ์ · ไม่ต้อง step-up
ตาม spec/09 §4. endpoint → สิทธิ์ที่ต้องมี เพราะเจตนาไม่ข้ามประตูใดของระบบ

## ตัดสินแล้ว (เจ้าของ · 2026-09-23)

- **เจตนาของคนชนะ config** — config `skip` แต่คนเลือก `trailing` = ใช้ `trailing` ในรอบนั้น ·
  config คือค่าตั้งต้นเมื่อไม่มีใครเลือก ส่วนเจตนาคือการกดของคนที่มีสิทธิ์ ·
  ประตูของ `late_entry()` ยังครบทุกบาน (ข้อจำกัดข้อ 3) เจตนาไม่ได้ข้ามอะไร
- **`wait_1h` ถูกปฏิเสธที่ endpoint** (422) ตราบที่ engine ยังไม่สร้างทางนี้ · รับไว้แล้วบันทึกว่ารอ
  จะทำให้คนเข้าใจว่าเลือกทางที่ใช้ได้ ทั้งที่ผลจริงคือไม่เข้าไม้ · วันที่ engine สร้าง `wait_1h`
  endpoint เลิกปฏิเสธพร้อมกัน
- **เลือกระหว่างที่ engine เดินอยู่ = มีผลกับ run ถัดไป** ตามกลไกข้างบน · หน้าจอต้องบอกตรงปุ่ม
  ว่าเจตนานี้ใช้กับ run ไหน ("มีผลเมื่อ start engine ครั้งถัดไป" เมื่อ engine กำลังเดิน)
  ไม่งั้นคนจะเข้าใจว่ากดแล้วเข้าไม้ทันที
