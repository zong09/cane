# ADR 23 · append-only บังคับด้วยสิทธิ์ของ DB ไม่ใช่ด้วยข้อตกลง

**สถานะ:** accepted

role `cane_engine` ได้ `SELECT` และ `INSERT` บนตารางข้อเท็จจริง (`bars`,
`funding_observations`, `decisions` และลูกของมัน, `fills`, …) **ไม่มี `UPDATE`/`DELETE` เลย**
ส่วน role `cane_console` อ่านได้ทั้งหมด แต่เขียนได้เฉพาะตาราง config/state

ตอนบันทึกเป็นไฟล์ JSONL คำว่า append-only เป็นแค่ข้อตกลงระหว่างคนเขียนโค้ด — โค้ดที่ผิดพลาด
เปิดไฟล์ด้วยโหมด `w` ทับประวัติทั้งไฟล์ได้และไม่มีอะไรขวาง ตอนนี้ DB ปฏิเสธให้

ผลที่ตามมาในตรรกะของ repository: การเขียนแท่งซ้ำใช้ `ON CONFLICT DO NOTHING` **ไม่ใช่ upsert**
เพราะ `DO UPDATE` ต้องการสิทธิ์ `UPDATE` ที่ engine ไม่มี — ตรรกะกับข้อบังคับพูดตรงกัน
ไม่ใช่ตรรกะที่ใจดีกว่าที่ DB ยอม และแท่งที่ปิดแล้วก็ไม่ควรถูกแก้อยู่แล้ว

**ข้อบังคับที่ประกาศไว้แต่ไม่มีใครลองยิงให้ล้ม คือข้อบังคับที่ไม่รู้ว่ามีผลหรือเปล่า** —
`tests/test_db_grants.py` จึงยิง `UPDATE`/`DELETE` ด้วย role engine แล้วยืนยันว่าถูกปฏิเสธจริง
เทสต์ชนิดนี้สำคัญเท่าเทสต์ที่ยืนยันว่า insert ผ่าน

**ผลตามมา:** role สร้างใน migration (ผ่าน `DO` block ที่ guard ด้วย `pg_roles` เพราะ
`CREATE ROLE` ไม่มี `IF NOT EXISTS` และ role เป็นของระดับ cluster) · GRANT อยู่ใน migration
ที่เพิ่มตารางนั้นเสมอ ตารางใหม่ที่ลืมให้สิทธิ์จะพังตอนเขียนครั้งแรก ซึ่งดีกว่าตารางที่ได้สิทธิ์
เกินมาแบบไม่มีใครสังเกต · ใน dev ที่ login user เป็นสมาชิกของทั้งสอง role การ `RESET ROLE`
ยกสิทธิ์คืนได้ กลไกนี้จึงกัน **ความผิดพลาดของโค้ด** ไม่ใช่กันคนที่ตั้งใจ
