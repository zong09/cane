# ADR 32 · `clientOrderId` ที่ส่งให้ venue เป็นรูปย่อของกุญแจตามสเปก

**สถานะ:** accepted · **เพิ่มเติม [spec/06 §กันสั่งซ้ำ (reconciliation)](../spec/06-risk-and-execution.md)**

กุญแจของ [spec/06 §กันสั่งซ้ำ (reconciliation)](../spec/06-risk-and-execution.md) คือ
`cane-{SYMBOL}-{bar_close_ts}-{side}-{leg}` · ตอนต่อ `CcxtBroker` จริง (ใบ 13) พบว่ามัน
**ยาวเกินที่ venue รับ**: Binance จำกัด `newClientOrderId` ไว้ที่ 36 อักษร
(`^[\.A-Z\:/a-z0-9_-]{1,36}$` ทั้ง fapi และ spot)

    cane-BTC/USDT-1787961600000-buy-open    36 อักษร · ผ่านพอดี
    cane-BTC/USDT-1787961600000-sell-close  38 อักษร · ถูกปฏิเสธ

ผลถ้าไม่แก้: **ขาเปิดส่งได้ ขาปิดส่งไม่ได้** ซึ่งบน perp ที่มี leverage คือ flip ที่ค้าง
ครึ่งทาง · และเหรียญที่ชื่อยาวกว่า BTC จะส่งไม่ได้แม้แต่ขาเปิด

## ตัดสิน

กุญแจตามสเปก**ไม่เปลี่ยน** — มันยังเป็นสิ่งที่ลง `fills.client_order_id` และ
`decision_orders.client_order_id` และยังเป็นทางเชื่อมระหว่างสองตารางนั้น

สิ่งที่ส่งให้ venue เป็นรูปย่อที่แปลงกลับได้: `cane-{bar_close_ts วินาที}-{side}-{leg}`
(26 อักษร **คงที่** ไม่ขึ้นกับความยาวชื่อเหรียญ) · การแปลงสองทิศอยู่ที่
`execution/reconcile.py` ที่เดียว (`venue_order_id()` / `spec_order_id()`)

- **ตัดชื่อเหรียญออกได้** เพราะ venue แยกออเดอร์ตามเหรียญอยู่แล้ว ทุก endpoint ที่เรียก
  ส่ง `symbol` ไปด้วยเสมอ ชื่อในกุญแจจึงเป็นข้อมูลซ้ำที่กินงบความยาว
- **วินาทีแทนมิลลิวินาที** ไม่เสียข้อมูล แท่ง 1h/1d ปิดที่ขอบวินาทีพอดี · เป็นรูปที่
  ตัวอย่างใน spec/06 เขียนไว้เองด้วย · เศษมิลลิวินาทีที่หลุดเข้ามา = `ValueError`
  ไม่ใช่ปัดทิ้งเงียบๆ (สองแท่งต่างกันได้กุญแจเดียวกันคือสิ่งเดียวที่กุญแจนี้กัน)

คุณสมบัติที่กุญแจมีหน้าที่รักษายังครบ: deterministic จากสิ่งที่รู้ก่อนส่ง · `leg` ยังอยู่
จึงยังแยกสองขาของ flip ที่เป็น `buy` เหมือนกัน · คำนำหน้า `cane-` ยังอยู่ จึงยังแยกออเดอร์
ของระบบออกจากที่คนไปกดเองที่หน้าเว็บ (ADR 19)

## ทำไมไม่ทำทางอื่น

- **เปลี่ยนกุญแจตามสเปกให้สั้นลงทั้งระบบ** — `decision_orders` ที่เขียนไปแล้วจะอ่านคู่กับ
  ของใหม่ไม่ได้ และ `fills` เป็น append-only (ADR 23) แก้ย้อนหลังไม่ได้
- **ตัดเฉพาะเครื่องหมาย `/` ออก** — ได้ 37 อักษร ยังเกิน · และยังโตตามชื่อเหรียญอยู่ดี
- **ปล่อยให้ ccxt ออก id ให้เอง** — id ที่สุ่มตอนส่งทำลายการกันสั่งซ้ำทั้งหมด ซึ่งเป็น
  เหตุผลเดียวที่กุญแจนี้มีอยู่

## ผลตามมา

- `spec_order_id()` ตัดส่วนต่อท้าย `-r{digest}` ของ stop ที่ถูกวางใหม่ทิ้งด้วย เพื่อให้ fill
  ของมันยังโยงกลับไปหา `decision_orders` แถวเดิมได้
- venue ที่รับ id ยาวกว่านี้ก็ยังได้รูปย่อเหมือนกัน — รูปเดียวทุก venue อ่านง่ายกว่ารูปที่
  เปลี่ยนตามปลายทาง
