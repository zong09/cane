# การตัดสินใจเชิงสถาปัตยกรรม

แต่ละข้อบันทึกไว้เพื่อให้คนที่มาทีหลังรู้ว่า **อะไรที่ถ้าเปลี่ยนแล้วต้องคิดใหม่ทั้งระบบ** ไม่ใช่แค่แก้บรรทัดเดียว

---

## 1. ใช้ Python

ccxt และ pandas เป็นมาตรฐานของงาน TA และการ port Pine Script มาเป็น pandas ตรงไปตรงมาที่สุด

**ผลตามมา:** ต้องระวังเรื่องความเร็วเมื่อ symbol เยอะขึ้น แต่ระบบนี้ตัดสินใจวันละครั้งต่อ symbol จึงไม่ใช่ข้อจำกัดจริง

---

## 2. ข้อมูลราคาจาก ccxt (Binance)

ข้อมูลย้อนหลังยาว ฟรี ดึงง่าย และ BTC เป็นสินทรัพย์หลักที่เอกสารต้นทางพูดถึง

---

## 3. ส่งคำสั่งผ่าน Broker interface ไม่ผูก venue

ยังไม่ตัดสินว่าจะเทรดที่ Binance หรือ Maxbit จึงกันไว้ด้วย interface

ตลาดคือ **USDT-M perpetual futures** ไม่ใช่ spot — venue ที่เลือกต้องมีตลาดนี้

**ผลตามมา:** ถ้าเลือก venue ที่ต่างจากแหล่งข้อมูล จะมี basis risk และ slippage เพิ่มที่ต้องจัดการ

---

## 4. LLM ตัดสินปัจจัยสนับสนุน โดยเห็นเฉพาะตัวเลข

ปัจจัยสามตัวเป็นการอ่านรูปแบบ ไม่ใช่เกณฑ์ตัวเลข การเขียนเป็น threshold แข็งคือการแอบตัดสินใจแทนคนออกแบบระบบ

เลือกป้อนตัวเลข+feature แทนภาพกราฟ เพราะทวนสอบได้ ถูกกว่า และ reproduce ได้

**ผลตามมา:** ถ้าจะเปลี่ยนไปใช้ vision ถือเป็นการเปลี่ยนสถาปัตยกรรม ต้องทบทวนการ cache และการทวนสอบใหม่ทั้งหมด

---

## 5. คำตัดสินของ LLM ต้องคงที่ต่อแท่ง

temperature 0 + structured output + cache ด้วย key `(symbol, timeframe, bar_close_ts, factor, prompt_hash)`

เอกสารต้นทางยืนบนหลัก "ระบบไม่เคยหลอกเรา" ระบบที่ตอบคนละอย่างสองครั้งบนข้อมูลเดิมถือว่าหลอก และเนื่องจากคำตัดสินแปลงเป็นขนาดไม้โดยตรง ความไม่คงที่จะกลายเป็นเงินจริงทันที

**ผลตามมา:** การแก้ prompt ทำให้ cache เก่าใช้ไม่ได้ ซึ่งเป็นเจตนา

---

## 6. LLM ล้มเหลว → ลงไม้ `base_pct`

สัญญาณ buy เป็น deterministic และไม่พึ่ง LLM กรณีนี้จึงตรงกับ "สัญญาณพื้นฐานที่ไม่มีปัจจัยสนับสนุน" ในเอกสารต้นทางพอดี

ทางเลือกที่ปฏิเสธ: ข้ามสัญญาณไปเลย — จะทำให้ความเสถียรของผู้ให้บริการ LLM กลายเป็นตัวแปรของกลยุทธ์

**ผลตามมา:** ต้องติดธงใน DecisionRecord ให้แยกออกจากกรณีที่ LLM ตัดสินจริงว่าไม่มีปัจจัย

---

## 7. ยิงออเดอร์อัตโนมัติภายใต้ risk limit ไม่มีคนกดยืนยันต่อไม้

เจ้าของระบบเลือกทางนี้หลังรับทราบข้อกังวลแล้ว

**ผลตามมา:** ชั้น risk กลายเป็นสิ่งเดียวที่กั้นระหว่างบั๊กกับเงินจริง จึงต้อง fail-closed ทุกจุด มี kill switch แบบ latched และมี reconciliation กันสั่งซ้ำ — ดู [spec/06](spec/06-risk-and-execution.md)

---

## 8. ขนาดไม้เป็น % ของ bucket ต่อ symbol **ต่อฝั่ง**

แต่ละ symbol มีเงินของตัวเอง แยกอีกชั้นเป็นฝั่ง long กับ short (`bucket_quote_long` / `bucket_quote_short`) ไม่ต้องมีกฎกันสัดส่วนรวมเกิน 100%

**ผลตามมา:** เงินที่ symbol หนึ่งไม่ได้ใช้ จะไม่ถูกเอาไปใช้กับ symbol อื่น และเงินที่ฝั่งหนึ่งไม่ได้ใช้ก็ไม่ถูกยืมไปอีกฝั่ง — ตั้งใจแลกประสิทธิภาพการใช้เงินกับความง่ายในการให้เหตุผล

---

## 9. paper กับ live เป็นคนละ profile โค้ดเส้นทางเดียวกัน

ความต่างอยู่ที่ค่า ไม่ใช่ที่ตรรกะ ถ้าตรรกะสองเส้นทางต่างกัน สิ่งที่ทดสอบใน paper จะไม่ใช่สิ่งที่รันจริง

**แก้ถ้อยคำ 2026-09-02:** เดิมเขียนว่า "คนละไฟล์" ตอนที่ config ย้ายลง DB (#18) มันกลายเป็น
**คนละชุดแถว** ที่แยกด้วยคอลัมน์ `profile` — เจตนาเดิม (โค้ดเส้นทางเดียวกัน) ไม่เปลี่ยน
และการแยกยังเข้มขึ้นด้วย เพราะ `profile` อยู่ในทุก unique key ของตารางที่ผูกโหมด
query ที่ลืมกรอง profile จึงชนกันเองตอนเขียน ไม่ใช่ไปโป๊ะตอนคอนโซลเอาไม้ paper ไปปนกับ live

---

## 10. ตัดสินใจบนแท่งที่ปิดแล้วเท่านั้น

สีของ Action Zone เปลี่ยนไปมาได้จนกว่าแท่งจะปิด (repainting)

**ผลตามมา:** ไม่รองรับโหมด fixed-timeframe ของ Pine Script ที่ใช้ `lookahead_on` และไม่ควรรองรับ

---

## 11. เฟสแรกยังไม่มี backtest engine แต่บังคับบันทึกให้ครบ

เจ้าของระบบเลือกทำ live signal bot ก่อน

**ผลตามมา:** ยังไม่มีหลักฐานเชิงตัวเลขว่าระบบมี edge จริงก่อนเริ่มใช้เงินจริง — เป็นความเสี่ยงที่รับทราบแล้ว การบังคับเขียน DecisionRecord ทุกแท่งทำให้ replay ย้อนหลังได้ในภายหลังโดยไม่ต้องรื้อระบบ

---

## 12. `base_pct` เป็นค่าคงที่ ไม่ผูกกับ confidence ของ LLM

ถ้าผูก ความไม่แน่นอนที่เราอุตส่าห์กันออกไปด้วยการ cache verdict จะกลับเข้ามาทางประตูหลัง

---

## 13. ไม่เอาเป้าราคาและส่วนจิตวิทยาจากเอกสารต้นทางเข้าโค้ด

เป้าราคา (§6) เป็นบทวิเคราะห์ ณ ช่วงเวลาหนึ่ง — hardcode แล้วจะยังตัดสินใจให้เราอยู่หลังสมมติฐานหมดอายุ
ส่วนจิตวิทยา (§5) เป็นวินัยของคน ไม่ใช่ logic ที่เครื่องรันได้

---

## 14. ตลาดคือ USDT-M perpetual futures มี leverage

> **ถูกแทนบางส่วนแล้วโดย [ข้อ 26](#26-ตลาดเป็นค่าต่อ-symbol-ไม่ใช่ค่าของทั้งระบบ)** — ข้อนี้ยังจริงสำหรับ
> เหรียญที่อยู่บน `usdtm_perp` แต่ไม่จริงในฐานะคำอธิบายของทั้งระบบอีกแล้ว ระบบเทรด `spot` ได้ด้วย

design handoff ยืนอยู่บนตลาดนี้ทั้งชุด (`market`, `leverage`, `max_leverage`, `min_liq_buffer_pct`, isolated + one-way, funding รายเหรียญ) และเจ้าของระบบยืนยันเลือกทางนี้ สเปกฉบับแรกเขียนว่า "ไม่ใช้ leverage" ซึ่งเป็นคนละระบบกัน

**ผลตามมา:** ไม้ถูกปิดโดย exchange ได้เองที่ราคา liquidation **แม้ยังไม่เกิดสัญญาณฝั่งตรงข้าม** — ขัดกับหลัก "ออกที่สัญญาณฝั่งตรงข้ามอย่างเดียว" ของเอกสารต้นทางโดยตรง ระบบกันด้วยตรรกะสัญญาณไม่ได้ กันได้ทางเดียวคือ `min_liq_buffer_pct` ซึ่งต้อง fail-closed อย่างเคร่งครัด: คำนวณระยะไม่ได้ = ไม่เปิด

---

## 15. เทรดสองฝั่ง long + short เต็มตัว

เอกสารต้นทางเป็น long-only แต่ Action Zone ให้สัญญาณสองฝั่งอยู่แล้วโดยธรรมชาติ (เขียวแรก / แดงแรก) และตลาด perp เปิด short ได้ตรงๆ การใช้แดงแรกเป็นแค่สัญญาณออกคือการทิ้งครึ่งหนึ่งของสัญญาณที่ระบบให้มาแล้ว

bucket แยกฝั่ง · confluence factor สองชุด ชุดละ 3 ตัว · flip สองขาในแท่งเดียว

**ผลตามมา:** ต้องมีโปรโตคอล flip ที่ **abort เป็นค่าตั้งต้น** — ขา 1 (ปิด) ไม่ fill ครบเมื่อไหร่ ให้ยกเลิกขา 2 ทั้งหมดแล้วบันทึก `flip_aborted` ถ้า retry หรือเปิดบางส่วน ระบบจะถือสองฝั่งพร้อมกันซึ่งละเมิด one-way และเป็นการถือความเสี่ยงสองทางที่ไม่มีชั้นไหนตั้งใจให้เกิด

---

## 16. คงการยิงอัตโนมัติเต็มรูปแบบ ไม่มี human gate ต่อไม้

design handoff เคยมีสิทธิ์ `กดยืนยันเข้าไม้` ในตาราง permission — ตัดออก เพราะขัดกับ #7 โดยตรง การใส่คนกลับเข้ามาตรงจุดเข้าไม้คือการเปิดช่องให้อคติกลับเข้ามาพอดีตรงที่ระบบตั้งใจตัดออก

คนกดได้สองอย่าง: **เลือกเส้นทาง cold start** และ **ปิดไม้ฉุกเฉิน** ทั้งคู่เป็นการลดความเสี่ยงหรือเลือกไม่ทำ ไม่มีปุ่มไหนที่คนกดแล้วเปิดไม้ใหม่ได้

**2026-09-01:** design handoff ชุด v3 ยังมีสิทธิ์ `กดยืนยันเข้าไม้ / ปิดไม้` อยู่ในตาราง permission
(ทั้งไฟล์ light, dark v3 และ `appendix/01`) เจ้าของระบบยืนยันมติเดิม — **สิทธิ์นี้ถูกตัดออก**
เป็น errata ที่ต้องแจ้งกลับไปที่ design ไม่ใช่การกลับมติ

## 17. stop loss ของ cold start ทางที่ 2 วางไว้ที่ exchange ไม่ใช่ประเมินฝั่ง engine

Broker interface ฉบับแรกมีแค่ `place / cancel / positions / balance` ไม่มีแนวคิดของ order type จึงตั้ง stop ไม่ได้ ทั้งที่ cold start ทางที่ 2 บังคับให้ตั้ง stop ที่เส้น Slow Trail ทันที

ทางเลือกที่ปฏิเสธ: ประเมิน stop ฝั่ง engine ตอนแท่งรายวันปิด — บน perp ที่มี leverage คือการป้องกันที่ตรวจวันละครั้ง ราคากระโดดข้ามคืนเดียวก็ถึง liquidation ได้ก่อน engine ตื่น

**ผลตามมา:** interface โตขึ้น — เพิ่ม order type (`stop_market`), `replace` (เส้น Slow Trail ขยับทุกแท่ง จึงต้องขยับ stop ตามโดยไม่เปิดหน้าต่างที่ไม้ไม่มี stop คุ้ม) และ `open_orders` (reconcile ต้องเห็น stop ที่ค้างอยู่ ไม่ใช่ดูแค่ position) · `PaperBroker` ต้องจำลอง stop fill ด้วย ไม่งั้นเส้นทางนี้ทดสอบใน paper ไม่ได้เลย ซึ่งขัดกับ #9 · `clientOrderId` ต้องมีชิ้น `leg` ไม่งั้นการกันสั่งซ้ำไม่นิยามสำหรับ stop order

**สิ่งที่เลือกไว้ให้ชัด:** kill switch latch แล้ว **บล็อกออเดอร์เปิดใหม่ แต่ไม่ยกเลิก stop ที่ป้องกันไม้เดิมอยู่** — fail-closed คือหยุดทำสิ่งใหม่ ไม่ใช่ปลดสิ่งที่ป้องกันอยู่

## 18. config อยู่ใน DB เป็นเวอร์ชันที่แก้ไม่ได้ · TOML เหลือหน้าที่ seed (เขียนใหม่ 2026-09-02)

แหล่งความจริงของ config คือตาราง `config_versions` กับลูกห้าตารางของมัน
ไฟล์ `config/*.toml` เหลือหน้าที่เดียว: เป็นทางเข้าครั้งแรกผ่าน `cane db seed`

**ทุกการแก้สร้างเวอร์ชันใหม่ ไม่ทับของเก่า** และเวอร์ชันเก่าอ่านได้ตลอดไป
`is_active` เป็นแค่ **ตัวชี้** ว่าเวอร์ชันไหนใช้อยู่ — คอนโซลได้สิทธิ์ `UPDATE`
เฉพาะคอลัมน์นั้นคอลัมน์เดียว (grant ระดับคอลัมน์) เนื้อของเวอร์ชันแก้ไม่ได้แม้แต่คอนโซล

### ข้อนี้เดิมว่าอะไร และทำไมเปลี่ยน

เดิมข้อนี้บอกว่า "config มาจากไฟล์ TOML อย่างเดียว ไม่มีชั้น environment มาทับ" ·
**เจตนาเดิมยังอยู่ครบ** — ค่าที่ระบบใช้ต้องไม่ต่างจากค่าที่คนเห็น และไม่มีชั้นไหนมาทับ
เงียบๆ · ที่เปลี่ยนคือ *ที่เก็บ* ไม่ใช่หลักการ

เหตุผลที่ทำให้ไฟล์ไม่พอ: คอนโซลแก้ไฟล์แล้วสั่งโหลดใหม่ (มติเดิมของ 2026-09-01)
ทำให้เวลาของการแก้ผูกกับ **เวลาที่ commit** ไม่ใช่กับ `bar_close_ts` ของแท่งที่ตัดสิน
พออ่านบันทึกย้อนหลังจึงตอบไม่ได้ว่า "แท่งนี้ตัดสินด้วย `base_pct` เท่าไร" นอกจากจะเดา
จาก git log · ทางแก้เดิมคือ snapshot ค่าลงทุกแถวบันทึก ซึ่งสร้างแหล่งความจริงที่สอง
ที่ขัดกับแหล่งแรกได้ · `decisions.config_version_id` เป็น FK ตรงไปที่เวอร์ชันที่ใช้จริง
ทำให้คำถามนั้นตอบได้โดยโครงสร้าง ไม่ใช่โดยการเดา

### สิ่งที่เสียไป และยอมรับแล้ว

**การรีวิว config ผ่าน `git diff` หายไป** มติเดิมตั้งใจใช้มันเป็นร่องรอย ("การแก้ทุกครั้ง
เห็นได้ใน git diff") ตอนนี้ไม่มีหน้า diff ให้คนรีวิวก่อน merge อีกแล้ว ·
`config_versions` ที่ immutable + `created_by_user_id` + `note` แทนได้ในแง่ *ใครแก้อะไร
เมื่อไร* และดีกว่าในแง่การผูกกับเวลาของแท่ง แต่ **ไม่ใช่ของแทนที่เท่ากัน** — การกันคนแก้
พลาดต้องย้ายไปอยู่ที่ permission กับหน้าจอยืนยัน ไม่ใช่ที่ขั้นตอน review PR

### ที่ไม่เปลี่ยน

- **ไม่มีชั้น environment มาทับ config** เหมือนเดิม — env มีแค่ `CANE_DB_DSN` และ
  credential ซึ่งเป็นคนละเรื่องกับค่าของกลยุทธ์ (#25)
- **ไม่มีโหมดเตือนแล้วไปต่อ** ค่าที่ไม่ผ่านกฎบันทึกเป็นเวอร์ชันไม่ได้ และไม่มีเวอร์ชัน
  active = ไม่เทรด ([spec/07](spec/07-data-and-config.md))
- **ไม่มีค่าตั้งต้นให้ risk limit** — เดิมคือการไม่ใส่ default ใน pydantic ตอนนี้เป็น
  `NOT NULL` ของ schema ด้วย บังคับสองชั้น
- state ของการทำงาน (kill switch, engine running, สวิตช์แจ้งเตือน) ยังแยกจาก config
  เหมือนเดิม เปลี่ยนแค่จากไฟล์ JSON ใน `var/state/` เป็นตารางของตัวเอง

### ตัวตรวจ: จาก path → เลขบรรทัด เป็น path → ฟิลด์

`validate.py` เดิมสแกนตัวอักษรดิบของไฟล์เพื่อทำแผนที่ path → เลขบรรทัด ให้คอนโซล
แสดง badge `L4 / L19` · ไม่มีไฟล์ก็ไม่มีบรรทัดให้ชี้ ตัวที่แทนคือ **path ของฟิลด์**
(`symbols[0].leverage`) ซึ่งตรงกับชื่อ input ในฟอร์มมากกว่าเลขบรรทัดอยู่แล้ว

`validate_settings()` เป็นประตูเดียวที่ค่าจากภายนอกผ่าน ไม่ว่าจะมาจากไฟล์ seed หรือ
จากฟอร์มคอนโซล — และมันยังจำเป็นแม้ DB จะมี `CHECK` ครบ เพราะ **CHECK ล้มที่ข้อแรก
ที่เจอเสมอ** ส่วนคนแก้ต้องเห็นทุกข้อในรอบเดียว · กฎที่ DB เขียนไม่ได้เลยคือ `leverage`
ต่อเหรียญเทียบกับ `max_leverage` ของ profile (กฎข้ามตาราง) จึงอยู่ที่ validator เท่านั้น

## 19. ของที่ค้างจาก `flip_aborted` ระบบไม่ปิดเอง คนปิดด้วยมือ

เมื่อขาปิดของ flip ทำงานไม่ครบ ส่วนที่เหลือยังเปิดค้างอยู่ที่ exchange โดยที่เส้นทาง
ออกตามปกติของมัน (สัญญาณฝั่งตรงข้าม) เพิ่งใช้ไปแล้วในแท่งนั้นและจะไม่เกิดซ้ำ
จนกว่าเทรนด์จะกลับอีกรอบ

เจ้าของระบบเลือก **คงพฤติกรรมนี้ไว้** และให้คนปิดเองผ่านสิทธิ์ "ปิดไม้ฉุกเฉิน"
ที่มีอยู่แล้วใน #16

ทางเลือกที่ปฏิเสธ:

1. **รีไทร์การปิดทุกแท่งจนกว่าจะหมด** — สร้างเส้นทางที่ระบบยิงคำสั่งนอกจังหวะสัญญาณ
   ซึ่งขัดกับหลักที่ว่าทุกการกระทำผูกกับแท่งที่ปิดแล้วและสัญญาณที่ตรวจสอบได้
2. **วาง stop ให้ส่วนที่เหลือ** — ขยาย stop จากเรื่องเฉพาะของ cold start ทางที่ 2
   (#17) ไปเป็นกลไกทั่วไป ทั้งที่เส้นทางปกติไม่มี stop โดยเจตนา

ทั้งสองทางเพิ่มโหมดการทำงานที่เกิดยากและทดสอบยาก บนเส้นทางที่ตัวมันเองก็เกิดยากอยู่แล้ว

**ผลตามมา — ข้อแลกเปลี่ยนที่ต้องจ่าย:** ไม้ที่ค้างเป็นไม้ที่มี leverage และไม่มี stop
อยู่จนกว่าคนจะเห็นและปิด ทางนี้จะใช้ได้จริงก็ต่อเมื่อระบบทำให้มัน **มองไม่พลาด**
จึงบังคับสามอย่าง: บันทึก `residual_qty` ตอนเกิด · เจอสถานะที่ระบบไม่ได้ตั้งใจถือเมื่อไหร่
ให้เขียน `unmanaged` **ซ้ำทุกแท่ง** ไม่ใช่ครั้งเดียว · คอนโซลแสดงเป็นสิ่งที่ต้องคนจัดการ
แยกจากไม้ปกติ ถ้าสามข้อนี้ไม่ครบ การตัดสินใจนี้จะกลายเป็นการเงียบใส่ความเสี่ยง

## 20. คอนโซลเป็น FastAPI + Jinja2 + HTMX ไม่ใช่ SPA

design handoff ชุด v3 แนะนำ React + TypeScript + Vite โดยให้เหตุผลว่า prototype เขียนเป็น
React เชิงโครงสร้าง จึง port ตรงที่สุด เจ้าของระบบ **ยืนยันทางเดิม**

เหตุผล: คอนโซลนี้เกือบทั้งหมดเป็น read-only view ของ state ที่ engine เขียนไว้ (`decisions.jsonl`,
`state/*.json`, ไฟล์ profile) การเพิ่ม build step กับภาษาที่สองเข้ามาในระบบที่มี deployable เดียว
คือการเพิ่มพื้นผิวที่ต้องดูแลโดยไม่ได้ตอบโจทย์ของงาน ส่วน fidelity สูงเป็นเรื่องของ CSS
ซึ่งทำได้เท่ากันทั้งสองทาง

**ผลตามมา:** interaction ที่ prototype ทำด้วย component state ต้องออกแบบใหม่เป็น server-rendered
partial — permission matrix แบบ draft, step-up modal, แผงแจ้งเตือน, accordion ฟอร์มคีย์ ทั้งหมดนี้
เป็น HTMX swap ไม่ใช่ client state ตรงไหนที่ต้องมี JS จริงๆ ให้เขียนเป็นสคริปต์เล็กแยก
ไม่ใช่ดึง framework เข้ามา

## 21. การแจ้งเตือนอยู่ในเฟสบอท ไม่ใช่เฟสคอนโซล

design แยกการแจ้งเตือนไว้เป็นงานของคอนโซล แต่ **event เกือบทั้งหมดเกิดที่ engine** — ส่งคำสั่ง
(พร้อม fill/margin/notional), ปิดแท่งรายวันประมวลผลครบ, config โหลดไม่ผ่าน, ไม้ที่ถืออยู่ขาดทุนหนัก
คอนโซลเป็นแค่ที่แสดงผลกับที่ตั้งค่า

เจ้าของระบบเลือก **แทรกเข้าเฟสบอท** (แก้ลำดับงานเดิมที่ให้ทำบอทจบก่อนแล้วค่อยแตะ console) เหตุผลที่หนักที่สุด: ถ้ารอถึง
เฟสคอนโซล ช่วง paper run ทั้งช่วงจะไม่มีการเตือนเลย ต้องนั่งเฝ้า log เอง ซึ่งเป็นช่วงที่ต้องการ
การเตือนมากที่สุดเพราะยังไม่รู้ว่าระบบมีพฤติกรรมอะไรที่ไม่คาดคิดบ้าง

**ผลตามมา:** เฟสบอทต้องมี event emitter กับช่องทาง LINE/Telegram ตั้งแต่แรก · สวิตช์เปิดปิด
อ่านจาก state ไม่ใช่จาก TOML (#18) · ส่วนที่ยังรอเฟสคอนโซลคือ **UI เท่านั้น** — กระดิ่ง แผงรายการ
และฟอร์มคีย์ · การส่งจริงต้องเช็คสวิตช์ของ **โหมดที่ยิง** ไม่ใช่โหมดที่คนกำลังดูอยู่

## 22. ข้อมูลทุกอย่างลง PostgreSQL · SQLAlchemy Core + Alembic ไม่ใช้ ORM

เดิมของแต่ละชนิดอยู่คนละที่: config เป็น TOML, แท่งราคาเป็น JSON ต่อ (symbol, timeframe),
DecisionRecord เป็น JSONL, kill switch กับสวิตช์แจ้งเตือนเป็น JSON ใน `var/state/`
เจ้าของระบบสั่งให้ยกเครื่องใหม่ให้ **ทุกอย่างลง DB อย่างเป็นระบบ**

กำไรที่หนักที่สุดสองข้อ ซึ่งเป็นสิ่งที่ไฟล์ทำไม่ได้ ไม่ใช่แค่ทำได้ยากกว่า:

1. **append-only บังคับได้จริง** ด้วยสิทธิ์ของ DB (#23)
2. **บันทึกผูกกับ config ที่ใช้ตัดสินแท่งนั้นได้** — `decisions.config_version_id` ชี้ไปที่
   เวอร์ชันที่ใช้จริง ไม่ต้อง snapshot `base_pct` / `bucket_quote` ลงทุกแถว และไม่ต้องหวังว่า
   เวลาของ git history จะเรียงตรงกับ `bar_close_ts` (ปัญหาที่ #18 สร้างไว้โดยไม่ได้ตั้งใจ)

**ใช้ SQLAlchemy Core + Alembic ไม่ใช่ ORM** — ระบบนี้ส่งข้อมูลไปมาด้วย frozen dataclass และ
ฉีด dependency เข้าทุกชั้นอยู่แล้ว session/identity-map ของ ORM ชนกับสไตล์นั้นตรงๆ และซ่อน SQL
ที่รันจริงไว้หลัง lazy-load ซึ่งเป็นสิ่งที่ระบบที่ยิงเงินจริงไม่ควรมี · repository คืน dataclass
เดิม (`Bar`, `FundingRate`, …) ชั้นบนจึงไม่รู้เลยว่ามี SQL อยู่

**ชนิดข้อมูล:** เงินและราคาเป็น `NUMERIC` · เวลาเป็น `BIGINT` epoch ms คงกฎ "ไม่มี `datetime`
ใน `src/`" ไว้ · จุดแปลง `NUMERIC` ↔ `float` อยู่ที่ repository **ที่เดียว** เพราะราคาที่เข้าสูตร
indicator ต้องเป็น `float` (golden test เทียบกับ TradingView) ขณะที่เงินใน ledger ต้องเป็น `Decimal`

**ผลตามมา — ราคาที่ต้องจ่ายและยอมรับแล้ว:**

- **ชุดเทสต์ไม่ hermetic อีกต่อไป** เทสต์ที่แตะ persistence ต้องมี Postgres จริง จึงแยกด้วย
  marker `db` และชุดที่ไม่แตะ DB ต้องยังรันได้โดยไม่มี service (`pytest -m "not db"`)
- ต้องมี migration เป็นชั้นงานใหม่ที่ต้องดูแล และการแก้ schema กลายเป็นเรื่องที่ต้องคิดถึง
  การถอยกลับด้วย ไม่ใช่แก้ dataclass แล้วจบ
- ของที่เคยอ่านได้ด้วย `cat` ต้องอ่านผ่าน SQL — คอนโซลได้ประโยชน์ แต่การไล่ปัญหาด้วยมือ
  ต้องมี `docker compose exec db psql` เป็นเครื่องมือประจำ

## 23. append-only บังคับด้วยสิทธิ์ของ DB ไม่ใช่ด้วยข้อตกลง

role `cane_engine` ได้ `SELECT` และ `INSERT` บนตารางข้อเท็จจริง (`bars`,
`funding_observations`, `decisions` และลูกของมัน, `fills`, …) **ไม่มี `UPDATE`/`DELETE` เลย**
ส่วน role `cane_console` อ่านได้ทั้งหมด แต่เขียนได้เฉพาะตาราง config/state

ตอนบันทึกเป็นไฟล์ JSONL คำว่า append-only เป็นแค่ข้อตกลงระหว่างคนเขียนโค้ด — โค้ดที่ผิดพลาด
เปิดไฟล์ด้วยโหมด `w` ทับประวัติทั้งไฟล์ได้และไม่มีอะไรขวาง ตอนนี้ DB ปฏิเสธให้

ผลที่ตามมาในตรรกะของ repository: การเขียนแท่งซ้ำใช้ `ON CONFLICT DO NOTHING` **ไม่ใช่ upsert**
เพราะ `DO UPDATE` ต้องการสิทธิ์ `UPDATE` ที่ engine ไม่มี — ตรรกะกับข้อบังคับพูดตรงกัน
ไม่ใช่ตรรกะที่ใจดีกว่าที่ DB ยอม และแท่งที่ปิดแล้วก็ไม่ควรถูกแก้อยู่แล้ว

**ข้อบังคับที่ประกาศไว้แต่ไม่มีใครลองยิงให้ล้ม คือข้อบังคับที่ไม่รู้ว่ามีผลหรือเปล่า** —
`tests/test_db_grants.py` จึงยิง `UPDATE`/`DELETE` ด้วย role engine แล้วยืนยันว่าถูกปฏิเสธจริง
เทสต์ชนิดนี้สำคัญเท่าเทสต์ที่ยืนยันว่า insert ผ่าน

**ผลตามมา:** role สร้างใน migration (ผ่าน `DO` block ที่ guard ด้วย `pg_roles` เพราะ
`CREATE ROLE` ไม่มี `IF NOT EXISTS` และ role เป็นของระดับ cluster) · GRANT อยู่ใน migration
ที่เพิ่มตารางนั้นเสมอ ตารางใหม่ที่ลืมให้สิทธิ์จะพังตอนเขียนครั้งแรก ซึ่งดีกว่าตารางที่ได้สิทธิ์
เกินมาแบบไม่มีใครสังเกต · ใน dev ที่ login user เป็นสมาชิกของทั้งสอง role การ `RESET ROLE`
ยกสิทธิ์คืนได้ กลไกนี้จึงกัน **ความผิดพลาดของโค้ด** ไม่ใช่กันคนที่ตั้งใจ

## 24. สิ่งที่คำนวณย้อนได้เป็น VIEW ไม่ใช่ตาราง

กำไรขาดทุนของไม้ที่ปิดแล้ว, P&L รายวันส่วนที่รับรู้แล้ว, จำนวนไม้ที่แพ้ติดกัน, ตัวเลขของ
compliance panel — ทั้งหมดคำนวณจาก `trades` + `fills` + `funding_charges` ได้ จึงเป็น **VIEW**
ห้ามเก็บเป็นตาราง

เหตุผล: ตารางสรุปที่เก็บไว้ซ้ำคือแหล่งความจริงที่สอง และมันจะขัดกับแหล่งแรกในวันที่มีบั๊ก
หรือมีการเขียนย้อนหลัง แล้วไม่มีใครรู้ว่าควรเชื่ออันไหน — ระบบที่รายงานเลขเงินต้องมีคำตอบ
เดียวต่อคำถามเดียวเสมอ

**ข้อยกเว้นที่มีเหตุผลของตัวเอง:** `max_daily_loss_pct` เป็น VIEW ล้วนไม่ได้ เพราะ
[spec/06](spec/06-risk-and-execution.md) บังคับให้นับ **กำไรขาดทุนที่ยังไม่ปิด** (mark-to-market)
ด้วย ซึ่งต้องมี mark price สดที่ไม่มีอยู่ในตารางไหนเลย · VIEW จึงให้แต่ส่วนที่รับรู้แล้ว
และตัวตัดสิน risk เป็น **ฟังก์ชันที่รับ mark price เข้ามา** ถ้าปล่อยให้คอนโซลอ่าน VIEW
แล้วเข้าใจว่าครบ ตัวเลขที่ได้จะต่ำกว่าความจริงในทางที่ปล่อยให้เปิดไม้เพิ่มขณะพอร์ตกำลังจม —
ซึ่งเป็นความผิดพลาดแบบเดียวกับที่สเปกเตือนไว้ตรงตัว

**ผลตามมา:** ต้นทุนที่หายต้องหายเสียงดัง — funding รอบ 8 ชม. เป็นกริดที่คำนวณได้ VIEW ของไม้
ที่ปิดแล้วจึงต้องคืนจำนวนรอบที่คาด/ที่บันทึกไว้/ที่ขาด และติดธง `cost_complete = false`
เมื่อขาด ไม่ใช่คืนยอดสุทธิที่ดูสมบูรณ์

## 25. ความลับไม่ลง DB แม้จะสั่งว่า "ทุกอย่างลง DB"

คีย์ exchange และ token ของ LINE/Telegram อยู่ใน `.env` ต่อไปตาม
[spec/07](spec/07-data-and-config.md) และ [spec/11](spec/11-notifications.md) ใน DB เก็บได้แค่
ของที่ไม่เป็นความลับ (`CANE_LINE_TO`, `telegram_chat_id`, `thread_id`)

เหตุผล: การเอา token ลงตารางแปลว่า dump ของ DB หนึ่งไฟล์ = คีย์ที่ยิงออเดอร์ได้รั่ว
นั่นคือการถอยหลังด้านความปลอดภัยเพื่อความสม่ำเสมอของคำว่า "ทุกอย่าง" ซึ่งไม่ใช่การแลกที่คุ้ม
ถ้าวันหนึ่งต้องให้ลง DB จริง ทางที่รับได้คือเก็บ **ciphertext** ที่เข้ารหัสด้วยคีย์ที่อยู่ใน
`.env` เพื่อให้ DB dump อย่างเดียวใช้ไม่ได้

**ของ auth ที่ไม่มีทางเลือก ต้องลง DB** — password เก็บเป็น argon2id hash · session เก็บ
**hash ของ token** ไม่ใช่ token · backup code เก็บเป็น hash · TOTP secret ต้องถอดกลับได้
จึงเก็บเป็น ciphertext ที่เข้ารหัสด้วยคีย์จาก `.env` ไม่ใช่ plaintext

**ผลตามมา:** ระบบยังต้องมี `.env` อยู่ การมี DB ไม่ได้ทำให้การตั้งค่าเครื่องใหม่เหลือขั้นเดียว ·
และคีย์ที่ใช้เข้ารหัส (`CANE_SECRET_KEY`) กลายเป็นของที่หายไม่ได้ — หายแล้ว TOTP ของทุกคนใช้ไม่ได้

(`config_symbols.market`) — profile เดียวถือ BTC บน perp และ ETH บน spot พร้อมกันได้
เหรียญหนึ่งเลือกได้ตลาดเดียว

ทางที่ปฏิเสธ: ทำ `market` เป็นค่าระดับ profile แล้วเปิดค่า `spot` เพิ่ม — จะแปลว่าการเทรดสองตลาด
พร้อมกันต้องมี profile ที่สาม ซึ่ง `profile_t` เป็นชุดปิด `live | paper` ที่มีความหมายคนละแกน
(โหมดจริง/จำลอง ไม่ใช่ชนิดตลาด) การยัดสองแกนเข้าคอลัมน์เดียวจะทำให้ "เทียบผลสองโหมดบนข้อมูล
ชุดเดียวกัน" ซึ่งเป็นเหตุผลทั้งหมดของการมี paper ทำไม่ได้อีก

**ผลตามมาที่ไม่สมมาตร และเป็นส่วนที่ต้องระวังที่สุด** — บน spot สิ่งเหล่านี้ **ไม่มีอยู่จริง**
ไม่ใช่ "มีแต่ค่าเป็นศูนย์":

- **ไม่มี liquidation** → `min_liq_buffer_pct` (ชั้นที่สามของ risk ตาม [spec/06](spec/06-risk-and-execution.md))
  **ไม่ถูกเรียกเลย** ไม่ใช่ถูกเรียกแล้วผ่านเสมอ · `decisions` ของแท่ง spot จึงมีแถว risk แค่สองชั้น
- **ไม่มี leverage** → `leverage = 1` เสมอ (บังคับด้วย CHECK) เพื่อให้สูตร `notional = margin × leverage`
  ของ [spec/05](spec/05-position-sizing.md) เดินเส้นทางเดียวทั้งสองตลาด · `max_leverage` เป็นเพดานของ perp
- **ไม่มี funding** → คอลัมน์ funding ต้องเป็น `NULL` ทั้งชุด ซึ่ง**คนละความหมายกับ "ดึงค่าไม่ได้"**
  ที่ `funding_observations` บันทึกไว้เป็นเหตุผล
- **ขายชอร์ตไม่ได้** → `allow_short` ต้อง false และไม่มี `bucket_quote_short` · สัญญาณแดงบนเหรียญ spot
  แปลว่า **ขายออกให้แบน จบ** (`leg = close` ล้วน) ไม่มีขาเปิดตาม จึง **ไม่มี flip บน spot**
  โปรโตคอลสองขาของ [spec/03](spec/03-trading-rules.md) เป็นของ perp เท่านั้น
- **ไม่มี `reduce_only`** — ขายบน spot คือขายของที่มี ไม่ใช่ธงของออเดอร์

**สิ่งที่ต้องแก้เพราะข้อนี้ และเป็นบั๊กข้อมูลจริง ไม่ใช่เรื่องรสนิยม:** `store_symbol()` ตัด `:USDT`
ทิ้งเพื่อให้ตารางเก็บรูปเดียวกับที่ config เขียน ผลคือ `BTC/USDT` ของ spot กับของ perp มีชื่อเดียวกัน
ในตาราง `bars` ที่กุญแจเดิมคือ `(symbol, timeframe, open_ts)` — สองตลาดจะทับกันเงียบๆ แล้ว indicator
จะคำนวณบนแท่งที่ปนกันสองตลาด · แก้โดย **เพิ่ม `market` เข้าไปในกุญแจ** ไม่ใช่เลิกตัด `:USDT`
เพราะการเข้ารหัสมิติไว้ในสตริงทำให้ `WHERE market = 'spot'` เขียนไม่ได้ ต้องไล่ `LIKE '%:USDT'` แทน

**ราคาที่จ่าย:** ทุกเส้นทางที่เคยสมมติได้ว่ามี leverage / funding / สองฝั่ง ต้องแตกตามตลาด —
ต้นทุนนี้จ่ายที่ขอบ (schema + CHECK + validator) ไม่ใช่กระจายเป็น `if market == ...` ทั่วโค้ด
